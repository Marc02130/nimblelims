# How to run the lab path

**Receive ≠ order ≠ work.** Three separate motions, not one chain:

- **Receive** (`/receive`) — the bench loop. Commit a tube, stay on the form, scan the next tube. That is the whole happy path.
- **Requested analysis** (`/asked-for`) — a **later look-up** of what a client or study asked for. Not a step in the receive motion, not the click after a commit.
- **Work** — later, unnumbered. Route is a planner (queued work order). **Start instantiates the first process only**; later processes need later starts. Route/Start does **not** start the whole chain and does not mint a process-of-processes. A request is not work.

This is a how-to, not a PRD. Marc keeps it current as features ship.

It is not sent through UTC. A time that is still today in the lab is accepted after UTC has rolled to the next day.

## 2. Accession (receive)

**UI:** Sample Mgmt → **Receive** (`/receive`).  
**API:** `POST /samples/receive`.  
`/accessioning` redirects here. There is no wizard.

1. Set sticky **sample type** and **project**. Session-sticky; they stay after each commit.
2. Scan or type the **primary barcode**. Optionally **Add** more barcodes for the **same** sample (more tubes, not aliquots). **Marc lock:** that second blood tube **may** carry its **own asked-for and own route** (equivalent aliquot / extra container on the same Sample). **Leadership Confirm:** two blood tubes → two process assignments (`container_id`); ELISA route and WGS/extract stay apart. Do not teach both tubes as one asked-for.
3. Optional temperature, client sample ID, **collection date**, **volume (µL)**, **condition**, and **thaw count**. Collection date is the calendar day the sample was drawn and cannot be a future day. Volume is zero to 10,000,000 µL. Thaw count is a whole number, zero or greater. A blank, a negative, or a non-number is refused. Leave a field blank to omit it.
4. **Receive**. Toast. Barcodes and those receipt fields clear. Sticky type, project, and container type stay. Focus returns to primary. A refused receive keeps what was typed.

**Happy path = stay on `/receive` and scan the next tube.** The loop ends on the form. Nothing else is owed at the bench: the sample is **Available for Testing** and waits. Do not send the tech to Asked-for after a commit.

**Receipt fields:** collection date is `date_sampled`. Volume, condition, and thaw count are `volume_ul`, `receipt_condition`, and `thaw_count` on the sample. They are sent on `POST /samples/receive`. When a receive layout exists (Tables & forms, screen `receive`), writable fields on that layout that are not already on this form appear under the built-in fields and are sent as `extra_fields`. With no saved layout, only the built-in fields show.

**One transaction:** Sample + first vessel (and any additional vessels) + Contents. Lab sample ID comes from the name template — **no sample-ID field**. Tube barcode is `containers.name`. Status is **Available for Testing**.

**Container type is not a receive decision.** RQ-AR-8 / Lab Ops **L3**: the lab **default tube** applies to **all** vessels on the call, **off the form** — no type picker in the scan loop. Plates are never receivable (non-1×1 → **400**). The current build still exposes a 1×1 container type on the form and still requires `container_type_id` on the API; that is CORE **drift** against RQ-AR-8, not the path this how-to teaches.

**Not on receive:** matrix (`samples.matrix` stays unset). No analysis picker, no requested analysis, no Route, no Test. Instrument type is chosen later on the LIMS run (the template `run_import` slot, or **Substitute instrument type** on that run), not at accession.

**Do not send `analysis_ids`.** The UI never offers an analysis picker. Omit the field or send `[]`. Non-empty → **422** before any write. Zero Tests. Zero Results.

Duplicate barcode → **409**, full rollback, stay on receive.

Client / no `sample:create` → no Receive nav or **403**.

## Later look-up: requested analysis (asked-for lake, P1)

*Deliberately outside the numbered path. It is a look-up, not a step in the bench motion.*

**Not the next step after receive.** Asked-for is a **separate motion**, done whenever someone needs to see or record what was asked for — reading a client request, a study plan, a paper form. Nobody is waiting on the bench for it, and it is **not** a Start queue. Saving a `requested` row creates no work. P2 exposes Route on that row for a distinct, later work-planning action.

**Copy lock:** say **requested analysis**. Do **not** say asked-for save assigns a Test, mints a work order, or starts work. Only the later explicit Route action can mint a work order.

**UI:** Sample Mgmt → **Asked-for** (`/asked-for`). Also a section on sample detail, which is where a tech normally meets it.
**API:** `POST /v1/asked-for` · `GET /v1/asked-for` · `POST /v1/asked-for/{id}/cancel`.
Handbook: [asked-for.md](asked-for.md).

**What a row is:** **requested analysis + TAT**, against an already-received sample. That is all.

1. The sample must already be received (identity + vessels), Available for Testing, Tests count 0.
2. Open Asked-for → **Record requested analysis**.
3. Pick sample(s), pick an active analysis, TAT of 0 or greater (days). Save. Stay on `/asked-for`.

One action may cover a set of samples (same analysis + TAT). The API still writes one row per sample. Status is `requested`. Cancel while `requested` is allowed; then you may record the same analysis again. Duplicate open `(sample, analysis)` → **409**.

**Save is not scientific assignment.** A saved row does **not** assign a Test, does **not** attach analytes, and does **not** make type-a-number legal. It does **not** create a Test, Result, Process, Experiment, LimsRun, or work_order. Receive freeze stays: non-empty `analysis_ids` on receive is still **422**.

**The lake accepts nonsense on purpose.** Qubit-on-blood may sit in it. Empty Route **422** “No routing-map row accepts this analysis, TAT, and sample type” is **Tobias-signed Pass** on `8cfa2a9`. Later-step type-gate at start (current tube) is **Met** on `9342439` (qPCR-on-blood / still-Blood **422** `route_sample_type`; not dest-type E2E). The lake and routing-map save do not run a chain-wide check.

Params: intent only. P1 sends `{}` OOB — do not type assay params here, and do not enter them in P1 UAT. The WO-7 lock is that params freeze at the **first LimsRun start** (P2), never on receive or asked-for. That freeze is **in code on `8cfa2a9`**; it is **not** QA-verified. Setup (`config:edit`) may `GET/PUT /analyses/{id}/param-defs`; empty catalog is the OOB path.

| Case | HTTP |
|------|------|
| Duplicate open `(sample, analysis)` | **409** (full rollback) |
| No project access / client write / hidden sample | **403** (not 404) |
| Discarded sample / inactive analysis / TAT &lt; 0 | **422** |
| Receive with non-empty `analysis_ids` | **422** (receive freeze) |

Keep a **second Lab Manager** user as backup for first-due, schedules, and event edits — that is another person with the existing Lab Manager role, not a new role. Labels and extra names for that backup are deferred. Events and downtime are bench work: the Configuring agent does not set **Track maintenance** (it lacks the SOP information to decide); only an Administrator turns the flag on or off. The agent's summary may note that an Administrator can turn on maintenance tracking. It cannot set schedules, first due, last done, next due, events, downtime, or uses. Turning **Track maintenance** off uses the admin dialog **Save** as the only confirm (no extra prompt) and writes `instrument_maintenance_audits`.

On the **Downtime** tab, record when an instrument goes down (`started_at` / `ended_at` as timestamps; `ended_at` empty while it is down). An `ended_at` in the future is **422**. Reason comes from the `downtime_reasons` list (seeded **Breakdown**, **Preventive maintenance**, **Calibration**, **Qualification**, **Facility**, **Other**; a removed reason is **422** `list_entry_inactive` on a new selection). Optional link to a maintenance event, optional note. Void a wrong row with Active off.

A new import and a new instrument use are refused (**422**) when the instrument is **down** (an open downtime row), **inactive**, **retired**, or **out of service**. When **Track maintenance** is on, they are also refused when there is no active schedule (`instrument_no_schedule`), when a schedule is awaiting its first due date (`instrument_awaiting_first_due`), or when a schedule is **overdue** (`next_due` before today). When it is off, maintenance and overdue do not block. Codes: `instrument_down`, `instrument_inactive`, `instrument_retired`, `instrument_out_of_service`, `instrument_overdue`, `instrument_no_schedule`, `instrument_awaiting_first_due`. The UI shows the flag and the API sentence as a stop. `GET /v1/instruments/{id}/eligibility` returns the same reason and `maintenance_tracked` without writing. `GET /v1/instruments?instrument_type_id=&eligible=true` is the picker: type filter plus server-side eligibility. Creating a LIMS run does not attach an instrument instance (`lims_runs` has no `instrument_id`). A template run snapshots `lims_runs.instrument_type_id` at start from the template's **run_import** slot. An ad hoc run (no template) must set that type on start (**422** `run_type_required` if it is missing). New runs do not have a null snapshot. The instrument is chosen at import and recorded on `instrument_uses`. Once the parser resolves an instrument, its type must match the run snapshot or the import is **422** `instrument_type_mismatch`. A leftover null snapshot on an old run is **422** `run_type_required` (the unchecked branch is gone). Then eligibility is checked. Both checks run before the import event, so a refused import writes nothing. CRO-lifecycle runs skip the type check. File import parses first, then locks the run and re-checks type and eligibility for both the instrument you sent and the one resolved from the parser. JSON `/import` without an instrument or CRO source is **422** `import_source_required` except for an Administrator (that exception is an `admin_override` import event with note `type not checked`).

On an experiment template, add an **Instruments** entry (**Tables & forms → Type → Instruments**, or **+ Instruments**) and define **slots** (`key`, `label`, `instrument_type_id`, `required`, `run_import?`). A LIMS run template must have exactly one `run_import` slot and that slot must have an active instrument type (**422** `instrument_entry_invalid` if it does not; **422** `run_template_type_required` if `create_run` is called without one). Inactive templates are hidden from create-run pickers (`GET /v1/experiment-templates` returns active rows). Lab Managers and Administrators see inactive templates in the catalog when they pass `include_inactive=true`. `?active=false` on a manager/admin listing returns only inactive rows. A technician who passes either flag still gets only active rows (not an error). Creating or starting a run from an inactive template is **422** `template_inactive`. An existing run still shows the template it was created from. Other slots may omit a type. After any `lims_runs` row references the template, changing the existing `run_import` type is **422** `run_import_type_locked` (setting a type where none existed is allowed). That template lock is the only remaining type lock: labs add and retire types with the status flag, and the person running the experiment may **Substitute instrument type** on that run (`POST /v1/lims-runs/{id}/substitute-instrument-type` with `{instrument_type_id, reason}`). Ownership is `lims_runs.created_by` (the run; there is no `started_by` and no `experiment_id` on `lims_runs`). The person who created the run may substitute, whether Lab Technician or Lab Manager; Administrator and Lab Manager may also substitute any non-terminal run. The template is never changed by a run. Existing imports keep the type they were checked against; new imports use the new type. On the experiment Instruments entry, add or remove instruments and slots (`PATCH /v1/entries/{id}` for slot types). Changing a slot type or pick voids the old `instrument_uses` row and inserts a new one; the template is not edited. Experiment uses are tracking only and are not tied to results. On the experiment or the LIMS run page, **Add instrument** / **Record use** (`experiment:manage`). Slot missing is **422** `instrument_slot_not_found`; a typed slot that does not match the instrument is **422** `instrument_type_mismatch`; then eligibility. Experiment uses are tracking only. An experiment use of an instrument that is not on the saved list is **422** `instrument_not_on_experiment`; add it first. A use with neither a run nor an experiment is **422** `use_target_required`. `used_on` is set to the lab day on the server. Un-voiding a use re-checks eligibility; a voided use stays voided if you send `active` false again. An inactive instrument type cannot be assigned (**422** `instrument_type_inactive`). A data parser may point at one instrument, one CRO source, or one instrument type (exactly one of the three). Matching tries the exact instrument first, then that instrument's type, and refuses (**422** `instrument_type_mismatch`) a type-scoped parser whose type is not the run's type, or an instrument-scoped parser whose instrument is not of the run's type. The Configuring agent may set the `run_import` slot type on experiment-templates POST/PATCH (confirm-before-apply). It cannot record uses, touch schedules or due dates, substitute a run type, grant anything, or bypass the type check. API: `/v1/instrument-types`, `/v1/instruments`, `/v1/cro-sources`, `/v1/instrument-maintenance-schedules`, `/v1/instrument-maintenance-events`, `/v1/instrument-downtime`, `/v1/instrument-uses`, `/v1/experiments/{id}/instruments`, `POST /v1/lims-runs/{id}/substitute-instrument-type`. There is no DELETE route.

**Instrument audit trail:** setting the first due date, turning a schedule's **Active** on or off, changing its interval, and voiding a maintenance event each write one `instrument_schedule_audits` row (who, when, old value, new value, and whether the schedule was overdue at the time). A void is final and does not write a new restore row. Existing `event_restore` rows stay. Changing only a schedule's kind or service vendor writes no row. Every change to **Track maintenance**, and creating an instrument with it off, writes one `instrument_maintenance_audits` row. The app can add rows to both tables but cannot edit or delete them. **Not this slice:** typed LIMS run templates, the type lock on a run, the instrument-type check at import, and **Substitute instrument type** with a required reason are E2 (migration `0115_instrument_type_slots`). E2 is in progress and not merged. Until it merges, nothing compares an instrument's type with a template or a run, and this how-to has no steps for them. Requirements: [`.docs/internal/prd/instrument-tracking/PRD.md`](../.docs/internal/prd/instrument-tracking/PRD.md).

**Dev leftover reagent uses (not a migration):** four test `reagent_uses` rows dated 2026-10-28 are neutralized by `python scripts/neutralize_dev_reagent_uses.py` from `backend/`, with `DATABASE_URL` set to that database. The default is a dry run and writes nothing. `--apply` sets `active` false, sets `quantity_used` to 0, and adds that quantity back onto the lot when `quantity_remaining` is not null. It refuses to write when the active match count is not 4 unless `--allow-count` is passed. A second apply finds nothing and exits 0. CI does not run this command, and the change that added it was not run against the dev database.

P1 does not instantiate a process from requested analysis. Classic `/tests` can still mint a Test for typing a number; that is **not** the request path.
