## 0. Scope

This Spec covers exactly:

1. The first slice, in order: (a) pin the R service; (b) known-answer tests (KATs) on the pinned service; (c) generic catalog functions. ELISA 4PL and the LAL STE-1.2 case are reference configurations for those tests only. They are not built-in configurations and not proposals (OQ-CALC-24).
2. A closed catalog of generic, named, versioned functions (Rolf B1), and calculation configurations built from them in a no-code builder. Assay thresholds are lab-bound constants on a configuration, not part of a function. NimbleLIMS is framework-first: the configuring agent configures it (CALC-REQ-47).
3. Stop rules for every stage, missing-data rules for every formula, and explicit units on every input and output. Each stage declares its on-fail outcome (CALC-REQ-48).
4. Immutability of released function versions and active configuration versions, result pinning, and no silent recompute. A calculation reads `results.raw_result`, including reference inputs (CALC-REQ-50), and writes the computed value to both `results.calculated_result` and `results.reported_result` (CALC-REQ-49).
5. Calculation-scoped, additive, incremental releases.
6. The configuring agent proposes configurations, and an Admin activates after the activation review (Rolf B2, CALC-REQ-45). The activation records the review document the dialog rendered (CALC-REQ-34).
7. What is out of scope (§5).

Anything else is not in this Spec.

## 2. Definitions

- **Function:** a generic, named calculation in the closed catalog, for example `fit_loglog_linear`. Identified by `name` plus an integer `version`. A function carries no assay threshold (Rolf B1).
- **Lock hash:** one value for one runnable R environment. It is SHA-256 of a UTF-8 preimage with three fields, separated by a single LF (U+000A), with no spaces and no trailing LF:

  `<base>\n<renv>\n<tree>`

  - `<base>` is 64 lowercase hex digits: the digest in the Dockerfile `FROM <image>@sha256:<base>`. It is the pinned base image, not the built service image.
  - `<renv>` is 64 lowercase hex digits: SHA-256 of the raw bytes of the committed `renv.lock`.
  - `<tree>` is the lowercase hex git tree id of `services/r-calculator` (`git rev-parse <commit>:services/r-calculator`). That tree is the function source. The catalog function version is not an input. It is stored on the result beside the lock hash (CALC-REQ-30).

  The lock hash is reported as 64 lowercase hex digits. Two builds of the same commit produce the same preimage and the same lock hash. The built image digest is required and is recorded alongside the lock hash. It is not an input to the lock hash, because a rebuild changes that digest. An image cannot know its own digest at build time, so the deploy supplies it at run time as the env var `R_IMAGE_DIGEST`, taken from the image it pulled by digest. `/health` gets `<base>` and `<tree>` from build args baked into the image, and computes `<renv>` from the `renv.lock` copied into the image. The backend's expected lock hash is recomputed from the commit the same way, with no image build.
- **Release:** a calculation-scoped bundle of new function versions, their KATs, and the lock hash they were proven on.
- **Validated catalog function:** a released function version whose KATs pass on the lock hash it serves (CALC-REQ-5, CALC-REQ-7). This is the only use of "validated" in this Spec (CALC-REQ-46).
- **Calculation configuration:** a no-code composition of catalog functions with input bindings, lab-bound constants, units, and per-stage on-fail declarations (CALC-REQ-48), for one analysis. It has an integer `version` and is immutable once active (CALC-REQ-40). The configuring agent proposes it (CALC-REQ-47). There is no separate agent that parses SOPs or instrument data.
- **Reference configuration:** the ELISA 4PL configuration and the LAL STE-1.2 configuration. They are test fixtures for KATs and end-to-end tests. They are not product seed, not built-in configurations, and not proposals (OQ-CALC-24).
- **Lab-bound constant:** a threshold or assay value supplied by a configuration, with a unit and a range check (CALC-REQ-41). Examples: |r| ≥ 0.980, %CV ≤ 25%, spike recovery 50–200%, EL, MVD.
- **Stage:** one function call inside a configuration. Each stage has a stop rule and an on-fail declaration (CALC-REQ-48).
- **Calculation attempt:** the record of one run of a configuration. It holds status, stop reason codes, lock hash, built image digest, configuration version, function versions, bound constant values, reference-input rows and values (CALC-REQ-50), the `dose_unknown` marker when that rule was used, and time (CALC-REQ-30). It always exists once a calculation call is accepted. A **result**, in this Spec, is a numeric or qualified output value on an attempt. An attempt can hold no result. The `results` table is a different thing. Its row links to the attempt (default, Marc to confirm; OQ-CALC-25). The column write is CALC-REQ-49.
- **Prose labels.** Where this Spec uses one of these three prose labels, it means exactly one code. The mapping is only here. "missing input" means `missing_input`. "repeat run" means `run_failed`. "curve not fitted" means `curve_not_fitted`. That code is the `fit_4pl` stage stop. In the ELISA reference configuration it is per plate. It implies no repeat run. The ELISA repeat policy is left to OQ-CALC-11.
- **Qualified results.** Each is a result with a stored qualifier kind, not missing data. There are three kinds:
  - `not_detected`, shown `<`. LAL configuration only: no onset by the cutoff (CALC-REQ-20).
  - `below_range`, shown `<`. A detected response or onset past the low-concentration end of the used calibrators (CALC-REQ-9, CALC-REQ-17).
  - `above_range`, shown `>`. A response or onset past the high-concentration end (CALC-REQ-9, CALC-REQ-17).

  `not_detected` and `below_range` display the same symbol and are stored as different kinds. The number after the symbol is the result's limit.
  - In the LAL reference configuration, the limit is computed by the backend (CALC-REQ-43). For `<`, L is the lowest used calibrator × DF ÷ mg/mL. For `>`, U is the highest used calibrator × DF ÷ mg/mL.
  - In the ELISA reference configuration, the limit is OQ-CALC-11.

## 3. Rules

### 3.1 Slice order

- **CALC-REQ-1 [Not built]** The first slice is delivered in order: (a) pin, then (b) KATs, then (c) the generic catalog functions. No (b) work merges before (a) is merged. No (c) function is released before its KATs pass on the pinned lock. ELISA 4PL and LAL STE-1.2 are not delivered. They are reference configurations for the KATs only (CALC-REQ-42, CALC-REQ-43, CALC-REQ-44), not built-in configurations and not proposals (OQ-CALC-24, Decided, Marc 2026-11-05). NimbleLIMS is framework-first: the configuring agent configures it (CALC-REQ-47).
  - AC: the merged history of the slice shows the pin before any KAT, and every (c) release record names a lock hash that has a passing KAT run. No migration, seed, or startup path inserts an ELISA or LAL configuration. The reference configurations exist only as test fixtures, and each pins only function versions that have a passing KAT run on that lock hash.

### 3.2 (a) Pin the R service

- **CALC-REQ-2 [Not built]** The R service base image is referenced by digest (`FROM <image>@sha256:<digest>`), not by tag. The lock hash uses that base digest (§2). The built image has its own digest, recorded alongside the lock hash, and that built digest is not part of the lock hash.
  - AC: the Dockerfile has no `FROM` line without `@sha256:`. Two builds from the same commit report the same lock hash on `/health`. Their built image digests may differ, and each is recorded. Recomputing §2 from the commit, without building, yields that same lock hash.
- **CALC-REQ-3 [Not built]** R packages come only from a committed `renv.lock` (`renv::restore()`). The image build does no unversioned `install.packages`. A restore that cannot match the lock fails the build.
  - AC: the Dockerfile restores from `renv.lock` and contains no `install.packages(` call. Changing one package version in `renv.lock` changes the lock hash.
- **CALC-REQ-4 [Not built]** `GET /health` reports `<base>`, `<renv>`, `<tree>`, the lock hash from §2, and the built image digest (`R_IMAGE_DIGEST`, §2). The built image digest is required. The backend holds the expected lock hash, recomputed from the commit. **Stop rule:** the backend refuses every calculation call and writes nothing when any of these is true: the reported lock hash differs from the expected one; `/health` does not report a lock hash; or `/health` does not report a built image digest, as `sha256:` followed by 64 lowercase hex digits.
  - AC: with a mismatched expected hash, a calculation request returns an error that names the mismatch, and no attempt or result row exists afterwards. With `R_IMAGE_DIGEST` unset, or not in the `sha256:<64 hex>` form, a calculation request is refused, names the missing digest, and writes nothing. The reported lock hash equals SHA-256 of the §2 preimage recomputed from the commit. Shipped `/health` reports only `drc_version` and `r_version`.
- **CALC-REQ-4a [Not built]** R sandbox and secrets (Günter H1, fail closed in his re-review B3). The R container runs as non-root, with a read-only root filesystem and tmpfs scratch, no network egress, and no host port. It has CPU, memory, and PID limits, and a per-request timeout enforced in both R and the backend. No database URL, credentials, or secrets are in the container, in image layers, or in build args. On `main` at `8e327c2`, `docker-compose.yml` already omits a host `ports:` block for `r-calculator` and sets no environment on that service. The Dockerfile has no `USER`. There is no read-only root, tmpfs, egress deny, or resource limit, and Plumber enforces no per-request timeout. The backend fit client times out at 60 s (`FIT_TIMEOUT_SECONDS` in `backend/app/services/r_calculator_client.py`), and the shipped R code bounds its profiled confidence interval at 5 s.
  - **Timeouts (default, Marc to confirm; OQ-CALC-16):** R stops a request after 50 s of wall-clock time. The backend stops waiting after 60 s, matching the shipped `FIT_TIMEOUT_SECONDS`. R's limit is shorter, so on a slow call R normally stops first and reports `r_timeout`. The backend's `backend_timeout` covers an R process that does not answer at all.
  - **Self-attestation:** `GET /health` reports a `sandbox` object measured inside the container at the time of the call:
    - `uid`: the process uid.
    - `root_read_only`: whether `/proc/self/mountinfo` shows the `/` mount as `ro`. A write probe alone is not enough, because a non-root process cannot write to `/` even on a writable root.
    - `scratch_tmpfs`: whether the scratch path is a tmpfs mount.
    - `egress_blocked`: whether an outbound connection probe fails.
    - `cpu_limited`, `memory_limited`, `pids_limited`: whether `cpu.max`, `memory.max`, and `pids.max` under `/sys/fs/cgroup` are set to a value other than `max`.
    - `forbidden_env_absent`: whether the environment has no `DATABASE_URL` and no name ending in `_KEY` or `_SECRET`.

    The backend checks that object at startup and again on every calculation call, together with the lock check (CALC-REQ-4). The backend never gets the Docker socket and never calls Docker. `docker inspect` is used only in deploy and CI, as the independent check that the container's real configuration matches what it reports.
  - **Fail closed:** the backend refuses every calculation call and writes nothing when any of these is true: the `sandbox` object is missing; any of its fields is missing; `uid` is 0; or any boolean is false.
  - **Timeout stop:** a timeout in R or in the backend stops that stage. It stores no result: no output value and no partial stage output. The calculation attempt (§2) still records status stopped and the system code `r_timeout` or `backend_timeout` (CALC-REQ-25). Those codes are not a user-entered reason (CALC-REQ-36).
  - AC: from inside the running container, an outbound connection attempt fails, a write outside the tmpfs scratch fails, and the process uid is not 0. The container environment, the image history, and the build args have no `DATABASE_URL`, no variable whose name ends in `_KEY`, and no variable whose name ends in `_SECRET`. `/health` reports every `sandbox` field, with each boolean true and `uid` not 0. With any field false, missing, or `uid` 0, a calculation call is refused and writes no attempt and no result. The backend container has no Docker socket mounted (no `/var/run/docker.sock`). In deploy and CI, `docker inspect` shows a read-only root filesystem and CPU, memory, and PID limits. An R call that runs past 50 s leaves an attempt with status stopped, `r_timeout`, and no result. A backend wait past 60 s leaves an attempt with status stopped, `backend_timeout`, and no result.

### 3.3 (b) Known-answer tests

- **CALC-REQ-5 [Not built]** Every released version of every generic catalog function has KATs: fixed inputs (with units), expected outputs (with units), and a declared tolerance per output (absolute or relative, with units). The KATs exercise the function on its own, with constants supplied by the test case, not by a configuration. KATs follow the split in CALC-REQ-37.
  - **R-side functions** (`fit_4pl`, `inverse_4pl`, `fit_loglog_linear`, `inverse_loglog_linear`): KATs run against the built, pinned image over HTTP, not against host R.
  - **Backend functions** (`replicate_mean_cv`, `spike_recovery`, `limit_compare`, `apply_dilution`, `convert_units`, `subtract`, and the range check before each inversion): KATs run against the backend's decimal code. They make no R call.
  - A backend KAT whose expected value is exact in decimal (for example recovery 50, a dilution of 5000 against a limit of 5000, |r| 0.98) uses tolerance 0.
  - **Serialiser unit test.** A unit test runs inside the pinned image, not on host R. It checks that R returns the shortest round-trip string for `0.026`, for `-0.98`, for `0.1 + 0.2`, and for `1/3`, and that each of those strings round-trips under R's own parser.
  - Per-configuration end-to-end KATs are CALC-REQ-44.
  - AC: each of the ten catalog functions has at least one KAT. The KAT run log names the image digest and lock hash it ran on, and lists each case as pass or fail with the observed value, expected value, and tolerance. It also names, for each case, the function name and version, and whether it ran against R or the backend. A backend-function KAT that calls R fails this rule. A function KAT that reads a constant from a configuration fails this rule. The serialiser unit test passes inside the pinned image for those four values; a run of it on host R does not meet this rule. Shipped `test_fit.R` runs on the host, is not in CI, and uses a 10% band on one synthetic set; it does not meet this rule.
- **CALC-REQ-6 [Not built]** KAT expected values for function KATs (CALC-REQ-5) and for the two configuration KATs (CALC-REQ-44) come from a cited source independent of the function under test (a published worked example, or a computation outside the R service that is recorded with the case). Synthetic or public data only. No SOP body text, no SOP PDF, and no client data in fixtures. Test cases recorded on an agent-drafted configuration may instead take expected values from system output, and are then flagged (CALC-REQ-45).
  - AC: each function KAT and configuration KAT case has a source citation. The STE-1.2 §6 worked example (EL 0.5 EU/mg, MVD 5000 at 10 mg/mL and HED 10 mg/kg) is a valid citation for the EL and MVD constants of the LAL configuration KAT, cited by section, not copied.
- **CALC-REQ-7 [Not built]** **Stop rule (engineering, not lab validation):** a function version cannot be part of a release unless its KATs pass on the release's lock hash. A new lock hash re-runs every KAT of every released version it will serve, and the two configuration KATs (CALC-REQ-44).
  - AC: an attempt to release a version with a failing or absent KAT run on that lock hash is refused. This is a software-release check. It is not the lab validation gate, which is out of scope (§5).
- **CALC-REQ-44 [Not built]** End-to-end KATs on the two reference configurations (Rolf B1, OQ-CALC-24). The ELISA reference configuration (CALC-REQ-42) and the LAL reference configuration (CALC-REQ-43) each have end-to-end KATs. One case runs the whole reference configuration on fixed run data, with its lab-bound constants, through every stage, against the pinned image and the backend together. Each case records the expected output and the declared on-fail outcome of every stage (CALC-REQ-48). They are an engineering check on the slice, like CALC-REQ-7. They are not a validation gate on activation (§5). The reference configurations are fixtures. They are not product seed data, not built-in configurations, and not proposals.
  - ELISA cases include `backend/tests/fixtures/elisa/IL6-PLT-0001_Gen5.csv`, with IL6-SER-0007 giving `above_range` (CALC-REQ-9), and a plate with three usable calibrator levels giving `curve_not_fitted`.
  - LAL cases are synthetic fixtures shaped like STE-1.2, cited by section, not copied. They include at least: a passing curve; |r| −0.975 giving `run_failed`; a QC %CV of 30% giving `run_failed`; recovery exactly 50 and exactly 200 passing; a dilution equal to MVD allowed; a sample at EL passing; a `not_detected` sample; the precedence case in CALC-REQ-43; and a dose-unknown sample whose result stores MVD 500 and the dose-unknown marker (CALC-REQ-11, CALC-REQ-30).
  - AC: the KAT run log names the reference configuration name and version, every function name and version it pinned, the lock hash, and the built image digest. Each listed case passes. A change to any pinned function version, any constant, or any stage on-fail declaration, without a new configuration version, fails this rule (CALC-REQ-40). A migration, seed, or proposal row that contains either reference configuration fails this rule.

### 3.4 (c) Generic catalog functions: fits and inversions (R side)

- **CALC-REQ-8 [Not built]** `fit_4pl` v1 fits a four-parameter logistic curve to calibrator responses against nominal calibrator concentrations. The fit runs in R (CALC-REQ-37).
  - Inputs: calibrator nominal concentration (concentration unit declared on the binding, for example pg/mL), calibrator response (unit declared on the binding, for example `OD`), replicate identity.
  - Outputs: bottom and top (response unit), slope (unit `1`), inflection point (same unit as the calibrator concentration), goodness-of-fit statistic (unit `1`), points used and excluded (count).
  - Missing-data rule: a calibrator replicate with no numeric response is excluded from the fit and counted as excluded. It is never treated as zero.
  - Stop rule: fewer than four calibrator levels with a numeric response, or a fit that does not converge, ends the stage with `curve_not_fitted`. No `inverse_4pl` stage that depends on it runs. Four levels is the parameter count of the model, not an assay threshold.
  - AC: a KAT with a published or independently computed 4PL set reproduces the four parameters within the declared tolerance. A set with three usable levels stops with `curve_not_fitted` and produces no parameters.
- **CALC-REQ-9 [Not built]** `inverse_4pl` v1 inverts a fitted 4PL curve for each response (back-calculation). Split (CALC-REQ-37):
  - The backend decides in-range or out-of-range in decimal from the raw response strings, before any R call.
  - R inverts in-range responses only.
  - The dilution step is a separate `apply_dilution` stage (CALC-REQ-38).
  - Inputs: curve parameters from `fit_4pl`, the response to invert (the replicate mean from `replicate_mean_cv`, sent as a decimal string), and the arithmetic-mean responses of the lowest-concentration and highest-concentration used calibrators.
  - Output: concentration in the calibrator concentration unit, or a qualified result.
  - Missing-data rule: no numeric response gives no concentration and a "missing input" flag. A response at or beyond an asymptote has no inverse and is flagged, not assigned a number.
  - Stop rule: the function never extrapolates. The range is the observed arithmetic-mean response of the lowest-concentration used calibrator and of the highest-concentration used calibrator. A response outside that span has no numeric concentration. Past the high-concentration calibrator's mean, the result is `above_range` (`>`), flagged, and the UI prompts dilute and rerun. Past the low-concentration calibrator's mean, the result is `below_range` (`<`) and flagged. Gates that read this result use CALC-REQ-37.
  - AC: a KAT response inside the range back-calculates within tolerance. A response past either end stores no number and gives the qualified kind for that end. A response past either end makes no R call.
- **CALC-REQ-12 [Not built]** `fit_loglog_linear` v1: linear regression of log10(y) on log10(x). The regression is a fit and runs in R (CALC-REQ-37). The non-positive input check below runs in the backend before the R call.
  - Inputs: x values (unit declared on the binding), y values (unit declared on the binding), point identity. Each point's y is a replicate mean computed by `replicate_mean_cv` and sent as a decimal string.
  - Outputs: slope (unit `1`), intercept (unit `1`, labelled `log10(<y unit>)`), correlation coefficient r (unit `1`), points used and dropped (count and identity).
  - Missing-data rule: a point with no y value is dropped and counted.
  - Stop rule: an x ≤ 0, or a y ≤ 0, or a replicate value ≤ 0 that would enter a mean, stops the stage. Nothing is passed to log10. The system code is `non_positive_log_input`. It is not a user-entered reason (CALC-REQ-36).
  - AC: a KAT with four points and known values reproduces slope, intercept, and r within tolerance. A KAT with an inverse relationship gives a negative slope. An x or y of 0 stops the stage with `non_positive_log_input` and stores no slope.
- **CALC-REQ-17 [Not built]** `inverse_loglog_linear` v1: inverts a log-log linear fit to give x from y (back-calculation). Split (CALC-REQ-37):
  - The backend decides in-range or qualified, in decimal, from the raw y string and the y means of the used endpoint points, before any R call.
  - R inverts in-range values only, and returns x as the shortest round-trip string.
  - The dilution and unit steps are separate stages (`apply_dilution`, CALC-REQ-38; `convert_units`, CALC-REQ-39).
  - Inputs: fit from `fit_loglog_linear`, the y value to invert (a replicate mean, as a decimal string), the y means of the used endpoint points.
  - Output: x in the x unit of the fit, or a qualified result.
  - Missing-data rule: no y value gives no x and a "missing input" flag.
  - Stop rule: a y outside the range of the used endpoint means is not extrapolated. Which end is `above_range` and which is `below_range` follows the sign of the slope: with a negative slope, a y below the mean of the highest-x used point is `above_range`, and a y above the mean of the lowest-x used point is `below_range`. Neither stores a number.
  - AC: a KAT y between the endpoint means back-calculates within tolerance. A y past either end stores no number, gives the qualified kind for that end, and makes no R call.

### 3.5 (c) Generic catalog functions: backend decimal steps

- **CALC-REQ-14 [Not built]** `replicate_mean_cv` v1: the arithmetic mean of a set of replicates, and %CV = SD / mean × 100. Runs in the backend, in decimal, with `sqrt` in the CALC-REQ-37 context. No R call. Its mean is the replicate mean that every fit and inversion receives (CALC-REQ-37).
  - Inputs: one or more replicate values in one shared unit.
  - Outputs: mean (in the replicate unit) and %CV in `%`.
  - Missing-data rule: no numeric replicate gives no mean. Fewer than two numeric replicates gives no %CV and a "replicate missing" flag (handling a missing single tube or split duplicate is OQ-CALC-8).
  - Stop rule: mean = 0 gives no %CV and a flag.
  - Open: SD form (n−1 or n) is OQ-CALC-5. Which quantity a configuration takes %CV on is set by the configuration (OQ-CALC-5 for the LAL configuration).
  - AC: replicates 1400.1 and 1400.3 give the mean exactly 1400.2. Replicates 100 and 110 give the %CV defined by the chosen SD form, within tolerance. One replicate gives a mean, no %CV, and the flag.
- **CALC-REQ-18 [Not built]** `spike_recovery` v1: recovery % = (spiked − unspiked) × 100 ÷ nominal spike. Runs in the backend, in decimal (CALC-REQ-37). No R call. The nominal spike is a lab-bound constant (CALC-REQ-41). The acceptance range is not part of this function. A configuration checks it with `limit_compare`.
  - Inputs: spiked and unspiked values in one shared unit, and the nominal spike in that unit.
  - Output: recovery in `%`.
  - Missing-data rule: no spiked value gives no recovery. How a qualified unspiked value enters is set by the configuration (OQ-CALC-7 for the LAL configuration).
  - AC: spiked 0.06 and unspiked 0.01 with nominal 0.05 give the unrounded decimal 100. The 0.026 case is two tests, not a natural R inversion. A backend-boundary KAT feeds the strings `0.026`, `0.001`, and `0.05`, makes no R call, and expects exactly 50. A contract test stubs the R client to return `0.026` for the spiked value, with unspiked `0.001` and spike `0.05`, and the backend parses those strings and gets exactly 50. A value carried as `0.025999999999999999` fails this rule. Spiked 0.171 and unspiked 0.071 give exactly 200. A binary value of 49.99999999999999 where the decimal is 50 fails this rule.
- **CALC-REQ-19 [Not built]** `limit_compare` v1: compares a value to a lab-bound limit and returns pass, fail, or no verdict. Runs in the backend, in decimal (CALC-REQ-37). No R call.
  - Inputs: the value (numeric or qualified, with its limit for a qualified result), and one of three comparison forms with its bound or bounds as lab-bound constants: at most (value ≤ limit), at least (value ≥ limit), or within (low ≤ value ≤ high). An optional absolute-value switch compares |value|. Every bound is inclusive (CALC-REQ-37).
  - Output: pass, fail, or no verdict with a flag.
  - **Qualified values against an "at most" limit.** For `not_detected` and `below_range`, the result's limit L ≤ limit passes. L > limit gives no verdict and the flag `limit_above_el`, because the true value can lie either side of the limit. For `above_range`, the result's limit U ≥ limit fails, because the true value is above U. U < limit gives no verdict and the flag `limit_below_el`, with a dilute-and-rerun prompt. The two flags keep their v1 spelling; "el" names whatever limit is compared against.
  - `not_detected` and `below_range` use the same rule but stay distinct stored kinds.
  - Missing-data rule: no value, or no limit, gives no verdict. The stage declaration names the missing-limit flag (CALC-REQ-48). The LAL reference fixture names `el_missing` (CALC-REQ-43).
  - When used in the LAL configuration, the precedence of no-verdict causes is CALC-REQ-43.
  - AC: 0.3 at most 0.5 passes; 0.5 at most 0.5 passes; 0.6 at most 0.5 fails. |−0.98| at least 0.980 passes, and |−0.97995| at least 0.980 fails. 50 and 200 within 50–200 pass; 49 fails. `not_detected` with L 0.4 at most 0.5 passes. `below_range` with L 0.4 at most 0.5 passes and stays stored as `below_range`, not `not_detected`. `not_detected` with L 0.6 at most 0.5 gives no verdict and `limit_above_el`. `above_range` with U 0.5 at most 0.5 fails. `above_range` with U 0.4 at most 0.5 gives no verdict and `limit_below_el`.
- **CALC-REQ-38 [Not built]** `apply_dilution` v1: value × dilution factor. Runs in the backend, in decimal. No R call.
  - Inputs: a value with its unit, and a dilution factor (unit `1`).
  - Output: the value in the same unit.
  - Missing-data rule: no dilution factor gives no output and a "missing input" flag.
  - Stop rule: a dilution factor < 1 is refused for that value.
  - AC: 0.026 × 100 gives exactly 2.6. A missing dilution factor gives `missing_input` and no output.
- **CALC-REQ-39 [Not built]** `convert_units` v1: two declared modes. Runs in the backend, in decimal. No R call.
  - Within-type conversion uses the `units` table multipliers (CALC-REQ-28). A conversion across unit types is refused.
  - Per-amount normalisation divides a value by a bound amount input. The output unit is the declared quotient, for example EU/mL ÷ mg/mL gives EU/mg.
  - Missing-data rule: no amount input gives no output and a "missing input" flag.
  - Stop rule: an amount ≤ 0 is refused.
  - AC: 2.6 EU/mL ÷ 10 mg/mL gives exactly 0.26 EU/mg. A missing amount gives `missing_input`. Converting `EU/kg` to `EU/mL` is refused.
- **CALC-REQ-51 [Not built]** `subtract` v1: output = minuend − subtrahend. No catalog function subtracts. `apply_dilution` multiplies and `convert_units` divides, so background subtraction is this function, not an assay-named one. It runs in the backend, in Python `decimal` (CALC-REQ-37). No R call.
  - Inputs: minuend and subtrahend, decimal strings in one shared unit. Either may be a reference input (CALC-REQ-50).
  - Output: the difference, in that unit.
  - Missing-data rule: a missing minuend or subtrahend that is not a reference input gives no output and `missing_input`. A missing, ambiguous, or stopped reference input stops first with that reference code (CALC-REQ-50), and `subtract` does not run.

  - AC: 2.572 − 0.050 gives exactly 2.522. The KAT calls no R route. A minuend equal to the negative-control value, so the difference is 0, stores `0` and does not stop. A missing subtrahend that is not a reference gives `missing_input` and no output.

### 3.6 Configurations and lab-bound constants

- **CALC-REQ-40 [Not built]** A calculation configuration has a name and an integer version. It pins the name and version of every catalog function it uses, every binding, every unit, every lab-bound constant, and every stage on-fail declaration (CALC-REQ-48). Once a configuration version is active, it is immutable. Any change to a pinned function version, a binding, a unit, a constant, or a stage declaration is a new configuration version. An active version is never edited or deleted. Results pin the configuration version (CALC-REQ-30). The ELISA and LAL reference configurations are not versions of a shipped configuration (OQ-CALC-24).
  - AC: an edit to an active configuration version is refused. The same change saved as a new version succeeds as a proposal, and the active version is unchanged. Changing only the flag one stage sets is refused on the active version and succeeds as a new version. A stored result shows the configuration name and version. No seed inserts the ELISA or LAL reference configuration.
- **CALC-REQ-41 [Not built]** Lab-bound constants. Every assay threshold and assay value is supplied by a configuration, not by a function (Rolf B1). Each constant has a kind from a closed list in code, which changes only through a PR-reviewed code change, like the catalog (CALC-REQ-22). The kind fixes its unit and its range check. The range checks are mathematical validity, not lab values:
  - `abs_correlation_min`: unit `1`, 0 < value ≤ 1.
  - `percent_cv_max`: unit `%`, 0 < value ≤ 100.
  - `percent_range`: unit `%`, 0 ≤ low ≤ high.
  - `min_point_count`: unit `1`, integer ≥ 2.
  - `endotoxin_limit`: unit `EU/mg`, value > 0.
  - `max_valid_dilution`: unit `1`, value ≥ 1.
  - `nominal_spike`: a concentration unit, value > 0.
  - `onset_cutoff`: unit `s`, value > 0.

  A constant may be a fixed value on the configuration or bound to a run or sample input. Either way the same range check applies. **Stop rule:** a configuration with a constant outside its range cannot be saved as a proposal and cannot be activated. A bound constant outside its range at run time gives no output for the stage that reads it.
  - AC: a configuration with `abs_correlation_min` 1.2, or `percent_cv_max` 0, is refused at save and names the constant. A bound EL of 0 at run time gives no verdict for that sample and names the constant. A proposal cannot change a kind's range.

When `non_positive_log_input` stops the LAL curve, the run summary records a stage stop naming `non_positive_log_input`. It is not `run_failed`. The repeat policy is left to OQ-CALC-19.
  - **Precedence.** Stage stops (`non_positive_log_input`, `r_timeout`, `backend_timeout`, `r_non_finite`, `curve_not_fitted`, `reference_missing`, `reference_ambiguous`, `reference_stopped`, `on_fail_undeclared`) and refusals before any attempt (lock mismatch, missing or bad built digest, sandbox failure; CALC-REQ-4, CALC-REQ-4a) take precedence over the per-sample places declared on the stages (CALC-REQ-48, CALC-REQ-43): `run_failed` > `dilution_invalid` > `el_missing` > `missing_input` > `limit_above_el` or `limit_below_el`. A stage stop is recorded on the attempt and stores no per-sample flag for that stage. A refusal writes nothing.
  - AC: each of those four conditions stores `run_failed` and names the condition. A run that fails any of them shows `run_failed` and no sample pass/fail. A `r_timeout`, `backend_timeout`, or `r_non_finite` is recorded as that stage stop and is not stored as `run_failed`. A LAL curve stopped with `non_positive_log_input` shows a run summary naming `non_positive_log_input`, not `run_failed`, and records no sample pass/fail. A lock, digest, or sandbox refusal writes no run summary.

### 3.9 Closed catalog and no-code builder

- **CALC-REQ-22 [Not built]** The catalog is closed and generic (Rolf B1). Version 1 contains exactly ten functions: `fit_4pl`, `inverse_4pl`, `fit_loglog_linear`, `inverse_loglog_linear`, `replicate_mean_cv`, `spike_recovery`, `limit_compare`, `apply_dilution`, `convert_units`, `subtract`. No catalog function is named for an assay, and none carries an assay threshold. Each entry declares name, version, every input and output with its unit, its missing-data rule, its stop rule, a plain-language description of its formula (CALC-REQ-45), and its KATs. Shipped dose-response `fit_compound` is not in the catalog until it is brought under these rules. The catalog changes only through a PR-reviewed code change (Günter H2). It never changes through the API, the UI, a database row, runtime config, or any agent. None of those paths can add a function or enable a version.
  - AC: the catalog lists exactly these ten entries, each with every declared field filled. No entry is named `elisa_*` or `lal_*`. An attempt to add or enable an entry through the API, the UI, a database write by the application role, runtime config, or an agent run is refused, and the catalog is unchanged. A new entry appears only after a reviewed pull request that changes the catalog in code is merged.
- **CALC-REQ-23 [Not built]** Calculations are configured only in a no-code builder: pick catalog functions, bind each input to a run column, an upstream stage output, a lab-bound constant, or a reference input (CALC-REQ-50), each with its unit, and declare each stage's on-fail outcome, flag, gated stages, and precedence place (CALC-REQ-48). There is no expression language and no free-text formula. A configuration proposed by the configuring agent (CALC-REQ-47) is opened in the same builder and uses the same bindings. The builder does not offer the ELISA or LAL reference configurations as built-in templates, seeds, or proposals (OQ-CALC-24).
  - AC: the builder offers only catalog functions; there is no text field that accepts a formula or code. A constant can only be bound with a kind from the closed list in CALC-REQ-41. Saving a stage with no on-fail declaration is refused. The ELISA and LAL reference configurations are not in the builder's template list and are not inserted as proposals.
- **CALC-REQ-48 [Not built]** Stage on-fail declarations (Tobias, blockers at 9308f7a). Every stage of a configuration declares all four of the following, and they are part of the configuration version (CALC-REQ-40):
  1. **On-fail outcome,** one of `run_failed`, `dilution_invalid`, sample verdict, or `flag`. A stage whose failure is a stage stop (CALC-REQ-25) declares that stop code instead of one of those four. `curve_not_fitted` and `non_positive_log_input` stay stage stops and are not declared as `run_failed`. There is no fail-open outcome (Günter). None of the four means the check failed and the stage passes, skips the failure, or continues as success. **Fail-closed default:** an undeclared outcome, or an outcome that is not one of the four and not a named stage-stop code, stops the stage with `on_fail_undeclared`. That stop stores no pass and no sample verdict. Dependent stages do not run. `calculated_result` stays null (CALC-REQ-49).
  2. **The flag it sets,** including the missing-limit flag when the stage reads a limit. The LAL reference fixture's EL stage sets `el_missing` when EL is absent.
  3. **The stages it gates:** later stages that do not run, or that do not receive this stage's output, when this stage fails or stops.
  4. **Its precedence place** in that configuration's per-sample list, or "above the list" for a stage stop. The places define the list. A configuration whose places disagree with each other is refused.

  The activation review shows all four for every stage (CALC-REQ-45). Changing any of them is a new configuration version.
  - AC: a proposal whose EL comparison stage has no declaration is refused and names the stage. A proposal that omits the missing-limit flag on a stage that reads a limit is refused. The LAL reference fixture shows `el_missing` on the EL stage at precedence place 3, and a KAT that deletes that declaration fails. Two stages that both claim precedence place 1 for different flags are refused. `fit_4pl` declaring `run_failed` for `curve_not_fitted` fails this rule. The activation dialog lists each stage's outcome, flag, gated stages, and place. An activation whose dialog omits them is refused. A stage whose on-fail outcome is missing, or is `pass`, stops with `on_fail_undeclared`, stores no pass, and does not write `calculated_result`. An outcome named `pass` is refused at save.
- **CALC-REQ-24 [Not built]** **Prohibited:** user code, scripts, plugins, a webhook runtime, and any generic "run R" (or run-any-code) endpoint. The R service exposes `/health`, one route per R-side function in CALC-REQ-37, and the pre-existing dose-response routes `POST /fit` and `POST /svg/full`. Those two stay, because dose-response on `main` calls them (`backend/app/services/r_calculator_client.py`). They stay until `fit_compound` is brought under these rules. The R-side functions are `fit_4pl`, `inverse_4pl`, `fit_loglog_linear`, and `inverse_loglog_linear`. `replicate_mean_cv`, `spike_recovery`, `limit_compare`, `apply_dilution`, `convert_units`, and `subtract` have no R route. No other route. A new route that runs caller-supplied code, or that accepts an unknown function or model name, is refused and does not fall back to a default.
  - AC: `POST /fit` and `POST /svg/full` still answer a dose-response call. The R service has no route for replicate means, %CV, spike recovery, the dilution step, unit conversion, limit comparison, or subtraction. A call to any other non-catalog path, or a body carrying code, is refused. A new route that is given an unknown model name is refused and does not run `LL.4`. ### 3.10 Stop rules, missing data, units

- **CALC-REQ-25 [Not built]** Every stage has a stop rule. When a stage stops, no later stage that depends on it runs. The stop and its reason code are recorded on the calculation attempt (§2), even when the stop leaves no result, as a timeout does (CALC-REQ-4a). Stage stops are `non_positive_log_input`, `r_timeout`, `backend_timeout`, `r_non_finite`, `curve_not_fitted`, `reference_missing`, `reference_ambiguous`, `reference_stopped`, and `on_fail_undeclared`. They sit above the per-sample list (CALC-REQ-43) and are not `run_failed`. A refusal before the call is accepted is different. A lock mismatch (CALC-REQ-4) or a sandbox failure (CALC-REQ-4a) writes no attempt.
  - AC: for each catalog function, a KAT case triggers its stop rule and shows that dependent stages did not run. A missing reference input stops with `reference_missing`, stores no per-sample flag, and is not `run_failed`.
- **CALC-REQ-26 [Not built]** Every formula has a missing-data rule. Missing input is never imputed, never zero, and never silently dropped. A below-limit (`<`) value is not missing.
  - AC: for each catalog function, a KAT case with a missing input shows the declared outcome.
- **CALC-REQ-27 [Partly shipped]** An excluded point (knockout or calibrator drop) is a recorded exclusion with who and when, and is reversible by recording a new calculation result. Shipped: `lims_run_data_exclusions` records `excluded_by`, `excluded_at`, and an optional reason for dose-response points. Not built: the same for calibrators and replicates on a calculation configuration.
  - AC: after a calibrator drop, the calculation result lists the dropped calibrator, the user, and the time.
- **CALC-REQ-28 [Not built]** Units are explicit on every input and every output, using the `units` table. Percentages use the existing `%`. The table gains an additive seed for `OD` (type `absorbance`), `s` (type `time`), `EU/kg` (type `endotoxin_per_body_mass`), `EU/mg` (type `endotoxin_per_mass`), `mg/kg` (type `dose`), and `1` (type `dimensionless`). Each of those six is multiplier 1 in its own type. None shares a type with `EU/mL` (type `activity`, migration `0092_concentration_unit_scales`) or with `mg/mL` (type `concentration`), so none converts onto those. The log-log intercept is unit `1` with label `log10(s)`, not a unit named log10 s. A binding whose unit does not match the function's declared unit (after a defined conversion within the same unit type) is refused at configuration time.
  - AC: the six names exist, each in the type named above. Binding a mg/kg value to an input declared in EU/mL is refused. `EU/kg` does not convert to `EU/mg` or to `EU/mL`. Every stored output carries its unit. Shipped: `concentration_unit` is sent to R and unused, and `dose_response_results` has no unit column. The six names are not in the seeded units at `8e327c2`.

### 3.11 Immutability, pinning, recompute

- **CALC-REQ-29 [Not built]** A released function version is immutable. Any change to a formula, default, tolerance, unit, stop rule, or missing-data rule is a new version. A released version is never edited or deleted. Configuration versions follow CALC-REQ-40.
  - AC: an edit to a released version is refused; the same change saved as a new version succeeds and the old version is unchanged.
- **CALC-REQ-30 [Not built]** Provenance for an accepted calculation is recorded on the calculation attempt (§2), and the `results` row links to that attempt. **Default, Marc to confirm (OQ-CALC-25):** those fields are not copied onto columns of `results`. The attempt holds the configuration name and version, the function name and version of every stage, the lock hash it ran on, the built image digest recorded alongside that hash, the value and unit of every constant bound to a run or sample input, each reference item's id, each replicate row id used, and each value read (CALC-REQ-50), and, when the dose-unknown rule was used, MVD 500 and the marker `dose_unknown` (CALC-REQ-11). The built digest is always present on an accepted attempt, because a call without it is refused (CALC-REQ-4). The configuration version, the function version, and the built digest are not inputs to the lock hash. A constant fixed on the configuration version is not copied onto the attempt. The bound values are what a per-sample EL verdict is audited against. The numeric output itself is `results.calculated_result` (CALC-REQ-49).
  - AC: the attempt linked from the `results` row shows the configuration version, each stage's function version, the lock hash, and the built image digest. The lock hash matches `/health` at the time it ran. The built digest may differ from the base digest inside the lock hash. Two samples in one run with bound EL 0.5 EU/mg and 0.2 EU/mg store those two values on their own attempts, and each verdict matches the stored EL. An attempt whose EL was bound to a sample input and that stores no EL value fails this rule. A dose-unknown sample's attempt stores MVD 500 and `dose_unknown`. A reference input stores the source row id and the value read. A fixed `abs_correlation_min` is not repeated on the attempt. Copying that provenance onto new columns of `results` fails this rule until Marc changes OQ-CALC-25.
- **CALC-REQ-31 [Partly shipped]** No silent recompute. A recompute is explicit. It writes a new calculation attempt that links to the attempt it replaces and records who triggered it, when, and why it ran (knockout, new function version, new configuration version, new lock). The previous attempt is kept, with its lock hash and values (CALC-REQ-32). On the same `results` row, the recompute is one audited system write to `calculated_result` (CALC-REQ-49). The database refuses every manual or user write to that column. This system write is the only exception that replaces an existing value. It also sets `reported_result` to the new calculated value, including when a lab tech had overridden `reported_result`. A stopped recompute sets `calculated_result` to null. What a stopped recompute does to `reported_result` is not decided (OQ-CALC-28). Shipped: a dose-response refit writes a new `dose_response_results` row with `fit_version + 1` and `superseded_by`. That shipped path is not this rule. Not built: the same-row system write, and the PDF SVG path, which re-fits on all points without the stored constraints instead of drawing the stored result.
  - AC: after a recompute, the same `results` row holds the new `calculated_result`, the new attempt links to the previous attempt, and the previous attempt still shows its old value and lock hash. A second `results` row for that recompute fails this rule. A user UPDATE of `calculated_result` fails. If `reported_result` was overridden to `0.030` and the new calculation is `0.040`, `reported_result` becomes `0.040`. A stopped recompute sets `calculated_result` to null and does not decide `reported_result` (OQ-CALC-28). Opening, exporting, or reporting a result never runs a calculation. Activating a new configuration version does not recompute earlier results.
- **CALC-REQ-32 [Not built]** A new lock hash never rewrites an earlier attempt. The earlier attempt keeps its lock hash and its values. `results.calculated_result` changes only when an explicit recompute runs (CALC-REQ-31).
  - AC: after a lock change with no recompute, every earlier attempt still shows its original lock hash and values, and `calculated_result` on the `results` row is unchanged.
- **CALC-REQ-49 [Not built]** Results mapping. Confirmed on `main` at `8e327c2`: `results.raw_result`, `results.reported_result`, and `results.calculated_result` are each `String(255)` and nullable (`backend/models/result.py`). Create stores `calculated_result` from the request body (`calculated_result=result_data.calculated_result` in `backend/app/routers/results.py`). Nothing computes it. Run publish writes `raw_result` only (`backend/app/services/result_promotion_service.py`, "raw_result only"; run-results Decision #2, "calculated deferred"). What publish promotes is not changed here (OQ-CALC-27).
  - A calculation reads each bound input from `results.raw_result`, through the configuration bindings (CALC-REQ-23), as a decimal string (CALC-REQ-37). Reference inputs are CALC-REQ-50.
  - **Decided (Marc, 2026-11-05, OQ-CALC-26).** The computed numeric output is written to both `results.calculated_result` and `results.reported_result`, as the same decimal string. `raw_result` is never overwritten.
  - A calculated row is a `results` row linked to an attempt that wrote `calculated_result`. The API refuses a manual or user write to `calculated_result` and stores nothing. The database refuses every manual or user UPDATE of `calculated_result`. The only UPDATE it accepts is the one audited system write of a recompute, on that same row (CALC-REQ-31). The first calculation, which sets `calculated_result` when it is null, is also a system write, not a user write. `raw_result` is never overwritten by either write.
  - To change a value by hand, a lab tech overwrites `reported_result` only. `calculated_result` and `raw_result` stay. A later recompute replaces `reported_result` with the new calculated value (CALC-REQ-31). The audit trail keeps the previous value, the new value, who, and when, for both the tech's override and the system write. On `main`, `results` has `modified_by` and `modified_at` (the `set_audit_timestamps` trigger in `backend/db/migrations/versions/0002_audit_triggers.py`) and no value-history table. `modified_at` alone does not meet this rule.
  - This Spec adds no required reason for that override (CALC-REQ-36). A reason may be a lab-configurable item. It is not required, and a missing reason is not refused.
  - A stopped attempt leaves `calculated_result` null, leaves `reported_result` unchanged, and records the stop code on the attempt (CALC-REQ-25). A refusal before the call is accepted writes no attempt (CALC-REQ-4, CALC-REQ-4a), leaves `calculated_result` null, and leaves `reported_result` unchanged.
  - AC: a calculation whose binding reads `raw_result` `0.026` leaves that column `0.026` and writes the same decimal string to both `calculated_result` and `reported_result`. A write that changes `raw_result` fails this rule. A JSON number in either written column fails this rule (CALC-REQ-37). An API update of `calculated_result` by a user is refused and the column is unchanged. A database UPDATE of `calculated_result` by a user does not commit. A system write may set it from null, and the audited recompute may replace it, on the same row. An update of `reported_result` to `0.030` succeeds, leaves `calculated_result` and `raw_result` unchanged, and the trail shows `0.026`, `0.030`, the user, and the time. A missing reason on that update is accepted. A recompute whose new value is `0.040` then sets both `calculated_result` and `reported_result` to `0.040`. An attempt stopped with `r_timeout` on the first calculation leaves `calculated_result` null, leaves `reported_result` as it was, and stores `r_timeout` on the attempt. A stopped recompute sets `calculated_result` to null and does not decide `reported_result` (OQ-CALC-28). A lock mismatch leaves both columns unchanged and writes no attempt. This rule does not change what publish writes.
- **CALC-REQ-50 [Not built]** Reference inputs (Marc, 2026-11-05). A calculation can read a value other than the result being calculated, for example the plate's negative control for `subtract` (CALC-REQ-51). A binding names a role, a scope, a setup, how the role is recognised, and how replicates are handled. The v1 roles are `negative_control`, `blank`, `calibrator`, and `qc`. A new role is a PR-reviewed code change, like the catalog (CALC-REQ-22). The scope is `experiment` or `lims_run`. The setup is a `results` row or a `lims_run_data` row. The lab configuration chooses the scope and the setup. Both scopes and both setups are supported. This Spec does not pick one.
  - **Scope `experiment`.** An experiment is a row in `experiments`. Its id is `experiments.id` (`backend/models/experiment.py`, class `Experiment`). `experiments` has no `project_id` and no `client_id`. Samples join an experiment through `experiment_sample_executions.experiment_id` (`backend/models/experiment.py`), with `replicate_number`, and optional `result_id` and `test_id`. The calculation is given one `experiments.id`. A source is in this scope when an `experiment_sample_executions` row for that source names that id.
  - **Scope `lims_run`.** `results.lims_run_id` references `lims_runs.id` (nullable, `ondelete='SET NULL'`). `lims_runs` has no `experiment_id`. `lims_run_data.lims_run_id` references the same run, and `lims_run_data.row_data` is JSONB (`backend/models/flexible_experiment.py`). The calculation is given one `lims_runs.id`. A source is in this scope when it names that id. The run is the plate.
  - **Role.** The binding names the field that marks the role and the value that field must equal. `samples.qc_type` is a `list_entries` id (`backend/models/sample.py`), not a role name. `experiment_sample_executions.role_in_experiment_id` is also a `list_entries` id. The binding stores that field and that list-entry id. A row matches when the named field equals that id. This Spec does not choose the field for a lab.
  - **One item, then its replicates.** A match is one distinct item plus that item's replicate rows. On the `results` setup, the item is one `samples.id` and the replicate rows are the `results` rows of that sample, distinguished by `results.replicate`. On the `lims_run_data` setup, the item is one `lims_run_data.sample_id` and the replicate rows are the rows of that sample. `lims_run_data` has no replicate column. The value of a `results` row is `raw_result`. The value of a `lims_run_data` row is the bound field of `row_data`, as a decimal string. The configuration, from the SOP, says which of two replicate rules applies. `average` sends those replicate values through `replicate_mean_cv` and uses the mean. `designated` uses one row: on the `results` setup, the row whose `results.replicate` equals the number the binding names; on the `lims_run_data` setup, the row whose `well_position` the binding names. A named replicate or well that is absent is `reference_missing`.
  - **Same client and project, under RLS (Günter F14).** The read runs as the caller. A `results` source is subject to `results_access` (`backend/db/migrations/versions/0029_enhance_rls_for_clients.py`): a non-admin sees it only through its test's sample and `has_project_access(samples.project_id)`. A `lims_run_data` source is subject to `lims_run_data_access` (`backend/db/migrations/versions/0049_rename_experiment_run_to_lims_run.py`): a non-admin sees it only with `has_experiment_access()` and a `created_by` in the same `users.client_id`. That policy does not check the project. `samples.project_id` references `projects.id`, and `projects.client_id` is the client (`backend/models/project.py`). On top of whichever policy applies, the source must be in the named scope and must be the same project, and therefore the same client, as the result being calculated. A source outside the scope, a source in another project, a source whose project belongs to another client, a source whose client or project cannot be shown, or a source the caller's RLS policy does not return, is `reference_missing`. The stop does not say that a row exists, and it returns no id and no value from that source.
  - Resolution is read-only. The calculation never writes `raw_result`, `calculated_result`, or `reported_result` on a referenced row.
  - **Stops, never a silent default.** No item is `reference_missing`. More than one distinct item is `reference_ambiguous`. Replicate rows of one item are not ambiguous. A matched `results` row whose linked attempt is stopped is `reference_stopped`. A `lims_run_data` row has no attempt and is not `reference_stopped`. Each code is a stage stop (CALC-REQ-25): above the per-sample list, not `run_failed`, and not zero, not the sample's own value, and not a skipped input. The attempt records the code. `calculated_result` stays null and `reported_result` is unchanged (CALC-REQ-49).
  - The attempt records the item id, each replicate row id used, the role, the scope, the setup, and each value read (CALC-REQ-30).
  - AC: a `subtract` stage bound to `negative_control` at scope `lims_run` reads that item and does not change its rows. On the `results` setup, two rows of one sample with `results.replicate` 1 and 2, configuration `average`, are one item: the mean comes from `replicate_mean_cv`, and the attempt stores both row ids and both values. The same two rows with `designated` 2 use only the row whose `results.replicate` is 2. On the `lims_run_data` setup, two wells of one `sample_id` with `average` are one item. `designated` names one `well_position` and uses only that well. Two distinct samples that both match the role stop with `reference_ambiguous`. A source on another `experiments.id`, or another `lims_runs.id`, stops with `reference_missing`. A source in another project, or another client, or a source `results_access` or `lims_run_data_access` does not return, stops with `reference_missing`, and the response contains no id and no value from it. A match whose attempt is stopped stops with `reference_stopped`. Each stop leaves `calculated_result` null, leaves `reported_result` unchanged, and is not stored as `run_failed`. A configuration can be saved with either scope and either setup.

### 3.15 Precision of gates

- **CALC-REQ-37 [Not built]** Gates run in the backend, not in R.
  - **Split between R and the backend.**
    - R does only the fits and the curve inversions: `fit_4pl`, `inverse_4pl`, `fit_loglog_linear` (slope, intercept, r), and `inverse_loglog_linear`.
    - The backend does all of the following, in Python `decimal`: `replicate_mean_cv`, `spike_recovery`, `limit_compare`, `apply_dilution`, `convert_units`, `subtract`, the in-range check before each inversion, the qualified-result limits (CALC-REQ-43), and the range checks on lab-bound constants (CALC-REQ-41). The backend computes every replicate mean in Python `decimal` and sends that mean to R as a decimal string. R never averages.
    - The backend does not recompute the regression or r from the points. It gates on R's r as received (next bullet).
  - **Inputs stay decimal strings.** Every gate input and every lab-bound constant is carried as a decimal string end to end: from the run data, binding, or constant, through the backend, and in every JSON body. It is never a JSON number and never an R double.
  - **Values that come from R.** R and drc fit outputs (for example slope, intercept, r, 4PL parameters) are binary doubles. R serialises each one as the **shortest round-trip** decimal string: the shortest string that parses back to the identical double (R tries 15, then 16, then 17 significant digits and takes the first that round-trips). It is not a fixed 17-digit string. So the double nearest 0.026 arrives as `0.026` and the double nearest −0.98 arrives as `-0.98`. The backend parses that string with Python `decimal`. That parsed value is the "unrounded decimal" for an R output, and it is what is stored and gated.
  - **Non-finite values stop.** NaN, Inf, −Inf, or NA in any R output stops that stage with the system code `r_non_finite` (CALC-REQ-25, CALC-REQ-36). The attempt is recorded and no result is stored. The backend never maps a non-finite value to a number, to a qualifier, or to a pass/fail.
  - **Arithmetic.** The backend evaluates every gate quantity with Python `decimal`, using a context of precision 50 and rounding `ROUND_HALF_EVEN`. Division, `log10`, and `sqrt` use that context. Within a formula, products are formed first and a single division is done last. Recovery is (spiked − unspiked) × 100 ÷ nominal spike. A limit is calibrator × DF ÷ mg/mL. So a quotient that is exact in decimal is exact here.
  - **Bounds are inclusive** in every `limit_compare`: at most, at least, and within. In the LAL configuration that means |r| ≥ 0.980, %CV ≤ 25%, 50% ≤ spike recovery ≤ 200%, dilution ≤ MVD, and sample result ≤ EL.
  - **Display.** Rounding is for display only. Each numeric output stores the unrounded decimal and the display precision declared for that output on the catalog entry. Display rounds half away from zero to that precision, and the result records the precision. No gate reads the displayed value. This Spec does not pick a global number of display decimal places.
  - AC: a dilution of 5000 against MVD 5000 is allowed. |r| = 0.97995 fails the 0.980 gate. Rounding it to three decimal places before the compare, which would show 0.980, is a failure of this rule. Recovery whose decimal value is 50 or 200 passes, including the pairs 0.026 with 0.001 and 0.171 with 0.071. A stored gate result that followed a binary value of 49.99999999999999 where the decimal is 50 fails this rule. Gate inputs and constants in request and response bodies are JSON strings, not JSON numbers; a JSON number in a gate input or constant is refused. A fit output from R arrives as its shortest round-trip string and is stored as that decimal. The 0.026 recovery and r of −0.98 are a backend-boundary test plus a stub-R contract test, not a natural R inversion. At the boundary, the strings `0.026`, `0.001`, and `0.05` give exactly 50% and pass, and the string `-0.98` passes |r| ≥ 0.980. The contract test stubs the R client to return those strings, and the backend parses them without turning them back into binary. The serialiser that produces such strings is the unit test in CALC-REQ-5. An R output of NaN or Inf stops the stage with `r_non_finite` and stores no result. The R service has no route that computes a replicate mean, %CV, recovery, the dilution step, a unit conversion, a limit comparison, or a subtraction. The stored row has the unrounded value and the recorded display precision, and the displayed rounding is not what the gate compared.

## 5. Out of scope

Stated explicitly, and not built by this Spec:

- **21 CFR Part 11** compliance.
- Any new required reason field.
- IC50 as the stress-case reference. The stress-case reference is the STE-1.2 LAL assay, and it is a test fixture only (CALC-REQ-43, OQ-CALC-24).
