## 0. Scope

This Spec covers exactly:

1. The first slice, in order: (a) pin the R service; (b) known-answer tests (KATs) on the pinned service; (c) generic catalog functions. ELISA 4PL and the LAL STE-1.2 case are reference configurations for those tests only. They are not built-in configurations and not proposals (OQ-CALC-24).
2. A closed catalog of generic, named, versioned functions (Rolf B1), and named versioned calculation configurations built from them in a no-code builder (CALC-REQ-40). The configuration lives on the existing analysis/analyte table. It is not a new configuration object. A threshold a calculation compares against is a configurable value bound directly in the calculation (CALC-REQ-23). Storing it in the [#258](https://github.com/Marc02130/nimblelims/issues/258) constants table, once that exists, is recommended, not required. It is not hardcoded in code. Constants are not implemented in this build. A constants table holding constants usable within a calculation, incorporated into the calculation configuration, is parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). Constants are not acceptance ranges for results. Acceptance limits on tests and sample results generally are a separate topic (§2). They are parked toward [#259](https://github.com/Marc02130/nimblelims/issues/259). [#258](https://github.com/Marc02130/nimblelims/issues/258) lists eleven constant identifiers and says Spec values go in its constants table. Those identifiers are the example under Calculation constant, not a requirement of this build. [#259](https://github.com/Marc02130/nimblelims/issues/259) describes that structure, a table keyed on QC type and analysis analyte; it is not yet designed. This supersedes the earlier stance that those threshold acceptance criteria wait on [#257](https://github.com/Marc02130/nimblelims/issues/257) (closed, absorbed into [#258](https://github.com/Marc02130/nimblelims/issues/258)). NimbleLIMS is framework-first: the configuring agent configures it (CALC-REQ-47).
3. Stop rules for every stage, missing-data rules for every formula, and units as locked in CALC-REQ-28. Units are not required to be explicit on every input and every output. Each stage declares its on-fail outcome (CALC-REQ-48).
4. Immutability of released function versions and active configuration versions, result pinning, and no silent recompute. On a LIMS run, a calculation reads values already in that same run (CALC-REQ-50) and writes calculated and reported on the result-entry row (CALC-REQ-49). Publish copies that row into official `results` and does not run a calculation. Recalculation is refused while the run is published. There is no standalone Results-screen path. Experiments do not write official `results`.
5. Calculation-scoped, additive, incremental releases.
6. The configuring agent proposes configurations, and an Admin activates after the activation review (Rolf B2, CALC-REQ-45). The activation records the review document the dialog rendered (CALC-REQ-34).
7. What is out of scope (§5).

Anything else is not in this Spec.

## 2. Definitions

- **Function:** a generic, named calculation in the closed catalog, for example `fit_loglog_linear`. Identified by `name` plus an integer `version`. A function carries no assay threshold (Rolf B1).
- **Lock hash:** one value for one runnable R environment. It is SHA-256 of a UTF-8 preimage with three fields, separated by a single LF (U+000A), with no spaces and no trailing LF:

  `<base>\n<renv>\n<tree>`

  - `<base>` is 64 lowercase hex digits: the digest in the Dockerfile `FROM <image>@sha256:<base>`. It is the pinned base image, not the built service image.
  - `<renv>` is 64 lowercase hex digits: SHA-256 of the raw bytes of the committed `renv.lock`.
  - `<tree>` is the lowercase hex git tree id of `services/r-calculator` (`git rev-parse <commit>:services/r-calculator`). That tree is the function source. The catalog function version is not an input. It is stored on the result beside the lock hash (CALC-REQ-30).

  The lock hash is reported as 64 lowercase hex digits. Two builds of the same commit produce the same preimage and the same lock hash. The built image digest is required and is recorded alongside the lock hash. It is not an input to the lock hash, because a rebuild changes that digest. An image cannot know its own digest at build time, so the deploy supplies it at run time as the env var `R_IMAGE_DIGEST`, taken from the image it pulled by digest. `/health` gets `<base>` and `<tree>` from build args baked into the image, and computes `<renv>` from the `renv.lock` copied into the image. The backend's expected lock hash is recomputed from the commit the same way, with no image build.
- **Release:** a calculation-scoped bundle of new function versions, their KATs, and the lock hash they were proven on.
- **Validated catalog function:** a released function version whose KATs pass on the lock hash it serves (CALC-REQ-5, CALC-REQ-7). This is the only use of "validated" in this Spec (CALC-REQ-46).
- **Calculation configuration:** a no-code composition of catalog functions with input bindings and per-stage on-fail declarations (CALC-REQ-48), for one analysis. It has a name and an integer `version` and is immutable once active (CALC-REQ-40). It lives on the existing analysis/analyte table, which may need columns added. It is not a new configuration object. The shipped free-text `analysis_analytes.calculation` column is not this configuration. Changing the calculation requires a new version of the analysis itself. The current analysis version is not edited in place. `analyses` has no version column on `main` at `8e327c2`. This Spec does not say how that version is stored, and it does not say whether the configuration's integer version and the analysis version are the same integer. The configuring agent proposes it (CALC-REQ-47). There is no separate agent that parses SOPs or instrument data. Units of the result live on the analysis/analyte, not on the calculation (CALC-REQ-28). Calculation constants are not implemented in this build (CALC-REQ-41). Until they exist, the calculation uses a configurable value embedded in the calculation (CALC-REQ-23). Recommendation (Marc, 2026-11-11): lab-bound values should be stored in the [#258](https://github.com/Marc02130/nimblelims/issues/258) constants table. Direct binding stays allowed, because not all use cases are known yet.
- **Reference configuration:** the ELISA 4PL configuration and the LAL STE-1.2 configuration. They are test fixtures for KATs and end-to-end tests. They are not product seed, not built-in configurations, and not proposals (OQ-CALC-24).
- **Calculation constant:** a value a calculation can use. A constants table would hold constants usable within a calculation, incorporated into the calculation configuration. That table is not implemented in this build. It is future scope, parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258) (CALC-REQ-41, Marc, 2026-11-10). [#258](https://github.com/Marc02130/nimblelims/issues/258) describes that table and lists the eleven constant identifiers. It says Spec values go in the table. It does not state columns, types, versioning, or how a configuration references a constant. Naming the concept does not bring constants into this build. Marc's 2026-11-07/08 lock still holds: lab-bound constants are not part of this Spec. A constant is not an acceptance range for a result. Until constants exist, a calculation binds values directly in the calculation. Those values are not hardcoded in code. Recommendation (Marc, 2026-11-11): lab-bound values should be stored in the [#258](https://github.com/Marc02130/nimblelims/issues/258) constants table. Direct binding stays allowed, because not all use cases are known yet. How a directly bound value is recorded on the attempt, how that binding is versioned, and what happens to those bindings when constants ship are open (OQ-CALC-46). Whether an attempt records the value is a separate open question (OQ-CALC-33): this Spec does not require that recording and does not forbid it. Constants are not collapsed into `high_value` / `low_value`.

- Example (not a requirement, not a default): [#258](https://github.com/Marc02130/nimblelims/issues/258) lists eleven constant identifiers, and it says Spec values go in its constants table. The identifiers are `abs_correlation_min`, `percent_cv_max`, `percent_range`, `min_point_count`, `endotoxin_limit`, `max_valid_dilution`, `nominal_spike`, `onset_cutoff`, `replicate_count`, `min_in_range`, and `max_remaining_span`. They illustrate a future constants table. The framework must support named constants usable in a calculation. This build does not implement that table, and these identifiers are not a builder menu and not a default. [#258](https://github.com/Marc02130/nimblelims/issues/258) does not state a check that `max_remaining_span` is greater than 0, and it does not state a `percent_range.high` bound.
- **Acceptance limit:** a limit on tests and sample results generally, not only on QC or control samples (Marc, 2026-11-10). Acceptance limits vary by test, by sample type, and by QC role, and each combination has its own range. Marc's examples of a QC role are a sample, a negative control, and a positive control. Those three are examples only. This Spec does not build a QC-role catalog.

- Example (not a requirement, not a default): pH between 0 and 4, or between 0 and 14; on one test, a sample from 0 to 100, a negative control from 0 to 5, and a positive control from 95 to 105. The framework must support a different range for each combination of test, sample type, and QC role.

- QC limits will often differ from sample limits. Acceptance ranges are per QC type and per analyte within an analysis. The structure that holds acceptance ranges for QC type is out of scope (§5). It is parked toward [#259](https://github.com/Marc02130/nimblelims/issues/259). Where an acceptance limit is stored, what happens when a value falls outside it, and how it is versioned are not specified (OQ-CALC-47). [#259](https://github.com/Marc02130/nimblelims/issues/259) lists storage columns and types, out-of-range behavior, versioning, and the relation to high_value/low_value as not yet designed. Acceptance limits are not the valid ranges on analytes or analysis/analytes (`high_value` / `low_value`, CALC-REQ-28). This Spec does not map one onto the other.
- **Stage:** one function call inside a configuration. Each stage has a stop rule and an on-fail declaration (CALC-REQ-48).
- **Result entry:** one record in experiment sample data for one replicate or for the average analyte. It is not an official `results` row. The columns this Spec adds are dedicated columns, not field-value cells (CALC-REQ-49). The name `lims_run_workspace_results` is removed. It is not a table in this Spec.
- **Official result:** a row in `results`. Official results are one valid final Test status plus the related results and replicates defined by the analysis/analyte. This Spec does not name that status ([#254](https://github.com/Marc02130/nimblelims/issues/254)). Publish copies the result entry into `results`. Publish does not run a calculation. This Spec does not use `official_set_id`, `superseded_at`, or `superseded_by_set_id`. Two generations are two Tests (CALC-REQ-55).
- **Calculation attempt:** the record of one run of a configuration. It holds status, stop reason codes, lock hash, built image digest, configuration version, function versions, reference-input rows and values (CALC-REQ-50), the values used, which points were knocked out (CALC-REQ-27), and time (CALC-REQ-30). Whether it also records a directly bound value, including an MVD used when the dose is unknown and a `dose_unknown` marker, is open (OQ-CALC-33, Marc, 2026-11-10). Constants that would hold that MVD later are parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). This Spec does not require that recording and does not forbid it. How a value bound directly under CALC-REQ-23 is recorded on the attempt is a separate open question (OQ-CALC-46). It always exists once a calculation call is accepted. A **result**, in this Spec, is a numeric, qualified, or pass/fail output value on an attempt. An attempt can hold no result. The result-entry row, and each official row written from that attempt, links to the attempt (default, Marc to confirm; OQ-CALC-25). The column write is CALC-REQ-49.
- **Knockout:** an action on one value. It is its own per-value flag, stored apart from `qualifiers`, with who, when, and a clear. It is not a qualifier-list pick (CALC-REQ-27). This Spec does not name a storage table for that flag.
- **Prose labels.** Where this Spec uses one of these three prose labels, it means exactly one code. The mapping is only here. "missing input" means `missing_input`. "repeat run" means `run_failed`. "curve not fitted" means `curve_not_fitted`. That code is the `fit_4pl` stage stop. In the ELISA reference configuration it is per plate. It implies no repeat run. The ELISA repeat policy is left to OQ-CALC-11.
- **Qualified results.** Each is a result with a stored qualifier kind, not missing data. There are three kinds:
  - `not_detected`. The configuration declares the cutoff type, high or low. A value past a high cutoff is stored with qualifier `>` and its limit. A value past a low cutoff is stored with qualifier `<` and its limit.

  - Example (not a requirement, not a default): a raw reading that feeds a calculation can be configured as an analyte, and a cutoff can bind on it. 7200 s is an example cutoff value. Which analyte a test has is lab configuration. The LAL fixture's configuration of that reading is in CALC-REQ-43. 7200 s is not the rule.
  - `below_range`, shown `<`. A detected response past the low-concentration end of the used calibrators (CALC-REQ-9, CALC-REQ-17).
  - `above_range`, shown `>`. A response past the high-concentration end (CALC-REQ-9, CALC-REQ-17).

  A low-cutoff `not_detected` and `below_range` display `<` and are stored as different kinds. A high-cutoff `not_detected` displays `>`. The number after the symbol is the result's limit.
  - `not_detected` is a value past a declared cutoff (CALC-REQ-20). A low cutoff stores `<` with the stored limit. A high cutoff stores `>` with the stored limit. The record is written. Reported is not null. There is no blank-result path. A written `not_detected` row, `<` or `>`, is not a stopped compute.

  - Example (not a requirement, not a default): in the LAL reference configuration, the backend computes the limit (CALC-REQ-43). For `<`, L is the lowest used calibrator × DF ÷ mg/mL. For `>`, U is the highest used calibrator × DF ÷ mg/mL. The framework must support a qualified-result limit computed in decimal from a calibrator, a dilution, and a concentration.
  - In the ELISA reference configuration, the limit is OQ-CALC-11.

## 3. Rules

### 3.1 Slice order

- **CALC-REQ-1 [Not built]** The first slice is delivered in order: (a) pin, then (b) KATs, then (c) the generic catalog functions. No (b) work merges before (a) is merged. No (c) function is released before its KATs pass on the pinned lock. ELISA 4PL and LAL STE-1.2 are not delivered. They are reference configurations for the KATs only (CALC-REQ-42, CALC-REQ-43, CALC-REQ-44), not built-in configurations and not proposals (OQ-CALC-24, Decided, Marc 2026-11-05). NimbleLIMS is framework-first: the configuring agent configures it (CALC-REQ-47).
  - AC: the merged history of the slice shows the pin before any KAT, and every (c) release record names a lock hash that has a passing KAT run. No migration, seed, or startup path inserts an ELISA or LAL configuration. The reference configurations exist only as test fixtures, and each pins only function versions that have a passing KAT run on that lock hash.

### 3.2 (a) Pin the R service

- **CALC-REQ-2 [Not built]** The R service base image is referenced by digest (`FROM <image>@sha256:<digest>`), not by tag. The lock hash uses that base digest (§2). The built image has its own digest, recorded alongside the lock hash, and that built digest is not part of the lock hash.
  - AC: the Dockerfile has no `FROM` line without `@sha256:`. Two builds from the same commit report the same lock hash on `/health`. Their built image digests may differ, and each is recorded. Recomputing §2 from the commit, without building, yields that same lock hash.
- **CALC-REQ-3 [Not built]** R packages come only from a committed `renv.lock` (`renv::restore()`). The image build does no unversioned `install.packages`. A restore that cannot match the lock fails the build.
  - AC: the Dockerfile restores from `renv.lock` and contains no `install.packages(` call. Changing one package version in `renv.lock` changes the lock hash.
- **CALC-REQ-4 [Not built]** `GET /health` reports `<base>`, `<renv>`, `<tree>`, the lock hash from §2, and the built image digest (`R_IMAGE_DIGEST`, §2). The built image digest is required. The backend holds the expected lock hash, recomputed from the commit. **Stop rule:** the backend refuses every calculation call and writes nothing when any of these is true: the reported lock hash differs from the expected one; `/health` does not report a lock hash; or `/health` does not report a built image digest, as `sha256:` followed by 64 lowercase hex digits.

- **CALC-REQ-4a [Not built]** R sandbox and secrets (Günter H1, fail closed in his re-review B3). The R container runs as non-root, with a read-only root filesystem and tmpfs scratch, no network egress, and no host port. It has CPU, memory, and PID limits, and a per-request timeout enforced in both R and the backend. No database URL, credentials, or secrets are in the container, in image layers, or in build args.   - **Timeouts (default, Marc to confirm; OQ-CALC-16):** R stops a request after 50 s of wall-clock time. The backend stops waiting after 60 s, matching the shipped `FIT_TIMEOUT_SECONDS`. R's limit is shorter, so on a slow call R normally stops first and reports `r_timeout`. The backend's `backend_timeout` covers an R process that does not answer at all.
  - **Self-attestation:** `GET /health` reports a `sandbox` object measured inside the container at the time of the call:
    - `uid`: the process uid.
    - `root_read_only`: whether `/proc/self/mountinfo` shows the `/` mount as `ro`. A write probe alone is not enough, because a non-root process cannot write to `/` even on a writable root.
    - `scratch_tmpfs`: whether the scratch path is a tmpfs mount.
    - `egress_blocked`: whether an outbound connection probe fails.
    - `cpu_limited`, `memory_limited`, `pids_limited`: whether `cpu.max`, `memory.max`, and `pids.max` under `/sys/fs/cgroup` are set to a value other than `max`.

The backend never gets the Docker socket and never calls Docker. `docker inspect` is used only in deploy and CI, as the independent check that the container's real configuration matches what it reports.
  - **Fail closed:** the backend refuses every calculation call and writes nothing when any of these is true: the `sandbox` object is missing; any of its fields is missing; `uid` is 0; or any boolean is false.
  - **Timeout stop:** a timeout in R or in the backend stops that stage. It stores no result: no output value and no partial stage output. The calculation attempt (§2) still records status stopped and the system code `r_timeout` or `backend_timeout` (CALC-REQ-25). Those codes are not a user-entered reason (CALC-REQ-36).
  - AC: from inside the running container, an outbound connection attempt fails, a write outside the tmpfs scratch fails, and the process uid is not 0. The container environment, the image history, and the build args have no `DATABASE_URL`, no variable whose name ends in `_KEY`, and no variable whose name ends in `_SECRET`. `/health` reports every `sandbox` field, with each boolean true and `uid` not 0. With any field false, missing, or `uid` 0, a calculation call is refused and writes no attempt and no result. The backend container has no Docker socket mounted (no `/var/run/docker.sock`). In deploy and CI, `docker inspect` shows a read-only root filesystem and CPU, memory, and PID limits. An R call that runs past 50 s leaves an attempt with status stopped, `r_timeout`, and no result. A backend wait past 60 s leaves an attempt with status stopped, `backend_timeout`, and no result.

### 3.4 (c) Generic catalog functions: fits and inversions (R side)

- **CALC-REQ-8 [Not built]** `fit_4pl` v1 fits a four-parameter logistic curve to calibrator responses against nominal calibrator concentrations. The fit runs in R (CALC-REQ-37).
  - Inputs: calibrator nominal concentration (concentration unit declared on the binding, for example pg/mL), calibrator response (unit declared on the binding, for example `OD`), replicate identity.
  - Outputs: bottom and top (response unit), slope (unit `1`), inflection point (same unit as the calibrator concentration), goodness-of-fit statistic (unit `1`), points used and excluded (count).
  - Missing-data rule: a calibrator replicate with no numeric response is excluded from the fit and counted as excluded. It is never treated as zero.
  - Stop rule: fewer than four calibrator levels with a numeric response, or a fit that does not converge, ends the stage with `curve_not_fitted`. No `inverse_4pl` stage that depends on it runs. Four levels is the parameter count of the model, not an assay threshold.
  - AC: a KAT with a published or independently computed 4PL set reproduces the four parameters within the declared tolerance. A set with three usable levels stops with `curve_not_fitted` and produces no parameters.
- **CALC-REQ-9 [Not built]** `inverse_4pl` v1 inverts a fitted 4PL curve for each response (back-calculation). Split (CALC-REQ-37):
  - The backend decides in-range or out-of-range in decimal from the raw response strings, before any R call.
  - R inverts in-range responses only.
  - The dilution step is a separate `apply_dilution` stage (CALC-REQ-38).
  - Inputs: curve parameters from `fit_4pl`, the response to invert (the replicate mean from `replicate_mean_cv`, sent as a decimal string), and the arithmetic-mean responses of the lowest-concentration and highest-concentration used calibrators.
  - Output: concentration in the calibrator concentration unit, or a qualified result.
  - Missing-data rule: no numeric response gives no concentration and a "missing input" flag. A response at or beyond an asymptote has no inverse and is flagged, not assigned a number.
  - Stop rule: the function never extrapolates. The range is the observed arithmetic-mean response of the lowest-concentration used calibrator and of the highest-concentration used calibrator. A response outside that span has no numeric concentration. Past the high-concentration calibrator's mean, the result is `above_range` (`>`), flagged, and the UI prompts dilute and rerun. Past the low-concentration calibrator's mean, the result is `below_range` (`<`) and flagged. Gates that read this result use CALC-REQ-37.
  - AC: a KAT response inside the range back-calculates within tolerance. A response past either end stores no number and gives the qualified kind for that end. A response past either end makes no R call.
- **CALC-REQ-12 [Not built]** `fit_loglog_linear` v1: linear regression of log10(y) on log10(x). The regression is a fit and runs in R (CALC-REQ-37). The non-positive input check below runs in the backend before the R call.
  - Inputs: x values (unit declared on the binding), y values (unit declared on the binding), point identity. Each point's y is a replicate mean computed by `replicate_mean_cv` and sent as a decimal string.
  - Outputs: slope (unit `1`), intercept (unit `1`, labelled `log10(<y unit>)`), correlation coefficient r (unit `1`), points used and dropped (count and identity).
  - Missing-data rule: a point with no y value is dropped and counted.
  - Stop rule: an x ≤ 0, or a y ≤ 0, or a replicate value ≤ 0 that would enter a mean, stops the stage. Nothing is passed to log10. The system code is `non_positive_log_input`. It is not a user-entered reason (CALC-REQ-36).
  - AC: a KAT with four points and known values reproduces slope, intercept, and r within tolerance. A KAT with an inverse relationship gives a negative slope. An x or y of 0 stops the stage with `non_positive_log_input` and stores no slope.
- **CALC-REQ-17 [Not built]** `inverse_loglog_linear` v1: inverts a log-log linear fit to give x from y (back-calculation). Split (CALC-REQ-37):
  - The backend decides in-range or qualified, in decimal, from the raw y string and the y means of the used endpoint points, before any R call.
  - R inverts in-range values only, and returns x as the shortest round-trip string.
  - The dilution and unit steps are separate stages (`apply_dilution`, CALC-REQ-38; `convert_units`, CALC-REQ-39).
  - Inputs: fit from `fit_loglog_linear`, the y value to invert (a replicate mean, as a decimal string), the y means of the used endpoint points.
  - Output: x in the x unit of the fit, or a qualified result.
  - Missing-data rule: no y value gives no x and a "missing input" flag.
  - Stop rule: a y outside the range of the used endpoint means is not extrapolated. Which end is `above_range` and which is `below_range` follows the sign of the slope. With a negative slope, a y below the mean of the highest-x used point is `above_range`, and a y above the mean of the lowest-x used point is `below_range`. With a positive slope, a y above the mean of the highest-x used point is `above_range`, and a y below the mean of the lowest-x used point is `below_range`. Neither stores a number.
  - AC: a KAT y between the endpoint means back-calculates within tolerance. A y past either end stores no number, gives the qualified kind for that end, and makes no R call.

### 3.5 (c) Generic catalog functions: backend decimal steps

- **CALC-REQ-14 [Not built]** `replicate_mean_cv` v1: the arithmetic mean of a set of replicates, and %CV = SD / mean × 100. Runs in the backend, in decimal, with `sqrt` in the CALC-REQ-37 context. No R call. Its mean is the replicate mean that every fit and inversion receives (CALC-REQ-37).
  - Inputs: one or more replicate values in one shared unit.
  - Outputs: mean (in the replicate unit) and %CV in `%`.
  - Missing-data rule: no numeric replicate gives no mean. Fewer than two numeric replicates gives no %CV and a "replicate missing" flag (handling a missing single tube or split duplicate is OQ-CALC-8).
  - Stop rule: mean = 0 gives no %CV and a flag.
  - Open: SD form (n−1 or n) is OQ-CALC-5. Which quantity a configuration takes %CV on is set by the configuration (OQ-CALC-5 for the LAL configuration).
  - AC: replicates 1400.1 and 1400.3 give the mean exactly 1400.2. Replicates 100 and 110 give the %CV defined by the chosen SD form, within tolerance. One replicate gives a mean, no %CV, and the flag.
- **CALC-REQ-18 [Not built]** `spike_recovery` v1: recovery % = (spiked − unspiked) × 100 ÷ nominal spike. Runs in the backend, in decimal (CALC-REQ-37). No R call. The nominal spike is an input. The nominal spike is a configurable value bound directly in the calculation (CALC-REQ-23). Storing it in the [#258](https://github.com/Marc02130/nimblelims/issues/258) constants table, once that exists, is recommended, not required. It is not hardcoded in code. Whether that range is a calculation constant or an acceptance range is not decided in this revision.

  - Output: recovery in `%`.
  - Missing-data rule: no spiked value gives no recovery. How a qualified unspiked value enters is set by the configuration (OQ-CALC-7 for the LAL configuration).

A contract test stubs the R client to return the spiked string, and the backend parses it without turning it back into binary.

- **CALC-REQ-19 [Not built]** `limit_compare` v1: compares a value to a limit and returns pass, fail, or no verdict. Runs in the backend, in decimal (CALC-REQ-37). No R call. The function stays in the catalog. Limit values a LAL or ELISA fixture would compare against, when they have no other source, are configurable values embedded in the calculation (CALC-REQ-23, Marc, 2026-11-10). They are not hardcoded in code. This Spec does not name the field that holds one. Constants that would hold them are parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). This supersedes the earlier stance that these acceptance criteria wait on [#257](https://github.com/Marc02130/nimblelims/issues/257) (closed, absorbed into [#258](https://github.com/Marc02130/nimblelims/issues/258)). It does not collapse them into analysis/analyte valid ranges. The acceptance criteria below supply bounds to the function itself. They are not fixture values.
  - Inputs: the value (numeric or qualified, with its limit for a qualified result), and one of three comparison forms with its bound or bounds: at most (value ≤ limit), at least (value ≥ limit), or within (low ≤ value ≤ high). An optional absolute-value switch compares |value|. Every bound is inclusive (CALC-REQ-37). A value equal to the bound passes.
  - Output: pass, fail, or no verdict with a flag.
  - A high cutoff is stored as `>` with its limit.

L > limit gives no verdict and the flag `limit_above_el`, because the true value can lie either side of the limit. For `above_range`, the result's limit U ≥ limit fails, because the true value is above U. U < limit gives no verdict and the flag `limit_below_el`, with a dilute-and-rerun prompt. The two flags keep their v1 spelling; "el" names whatever limit is compared against.
  - `not_detected` and `below_range` use the same rule but stay distinct stored kinds.
  - Missing-data rule: no value, or no limit, gives no verdict. The stage declaration names the missing-limit flag (CALC-REQ-48).

  - Example (not a requirement, not a default): the LAL reference fixture names `el_missing` (CALC-REQ-43), and its precedence of no-verdict causes is in CALC-REQ-43. `el_missing` is not the required flag.
  - AC: a value equal to an at-most bound passes, and a value above it fails. A value equal to either end of a within-bound passes, and a value outside it fails. An absolute-value comparison uses the absolute value and the same inclusive bound. `not_detected` whose stored limit is at or under an at-most bound passes. `below_range` with the same limit passes and stays stored as `below_range`, not `not_detected`. `not_detected` whose stored limit is above that bound gives no verdict and `limit_above_el`. `above_range` whose stored limit is at or above an at-most bound fails. `above_range` whose stored limit is below that bound gives no verdict and `limit_below_el`.

  - Example (not a requirement, not a default): 0.5 at most 0.5 passes and 0.6 fails; |−0.98| at least 0.980 passes and |−0.97995| at least 0.980 fails; 50 and 200 within 50–200 pass and 49 fails; L 0.4 at most 0.5 passes and L 0.6 gives `limit_above_el`; U 0.5 at most 0.5 fails and U 0.4 gives `limit_below_el`. The framework must support those comparisons. The numbers are not assay rules.

- **CALC-REQ-51 [Not built]** `subtract` v1: output = minuend − subtrahend. ### 3.6 Configurations

  - Per value, and not assay-specific. One well, one replicate, or one target can be knocked out without the others. qPCR is an example only. It is not in the first slice (OQ-CALC-24).

- **CALC-REQ-28 [Not built]** Units (Marc, 2026-11-07/08). Units live on the analysis/analyte, not on the calculation. Catalog functions keep the input and output units their own rules declare. This Spec does not add a gate for that.
  - **Pass/fail.** A calculation may set calculated and reported to pass or fail from a numeric result, with no units and no conversion. This Spec does not design that path further.
  - **Not required everywhere.** Units are not required to be explicit on every input or every output. Output units depend on the result. Pass/fail has no units.

### 3.15 Precision of gates

- **CALC-REQ-37 [Not built]** Gates run in the backend, not in R.
  - **Split between R and the backend.**
    - R does only the fits and the curve inversions: `fit_4pl`, `inverse_4pl`, `fit_loglog_linear` (slope, intercept, r), and `inverse_loglog_linear`.
    - The backend does all of the following, in Python `decimal`: `replicate_mean_cv`, `spike_recovery`, `limit_compare`, `apply_dilution`, `convert_units`, `subtract`, `copy_raw`, the in-range check before each inversion, and the qualified-result limits (CALC-REQ-43). The backend computes every replicate mean in Python `decimal` and sends that mean to R as a decimal string. R never averages. Lab-bound constant range checks are not in this Spec (CALC-REQ-41).
    - The backend does not recompute the regression or r from the points. It gates on R's r as received (next bullet).
  - **Inputs stay decimal strings.** Every gate input is carried as a decimal string end to end: from the run data or the binding, through the backend, and in every JSON body. It is never a JSON number and never an R double.
  - **Values that come from R.** R and drc fit outputs (for example slope, intercept, r, 4PL parameters) are binary doubles. R serialises each one as the **shortest round-trip** decimal string: the shortest string that parses back to the identical double (R tries 15, then 16, then 17 significant digits and takes the first that round-trips). It is not a fixed 17-digit string. The backend parses that string with Python `decimal`.

  - Example (not a requirement, not a default): the double nearest 0.026 arrives as `0.026`, and the double nearest −0.98 arrives as `-0.98`. The framework must keep the shortest round-trip string. Those two strings are not assay rules.

  - That parsed value is the "unrounded decimal" for an R output, and it is what is stored and gated.
  - **Non-finite values stop.** NaN, Inf, −Inf, or NA in any R output stops that stage with the system code `r_non_finite` (CALC-REQ-25, CALC-REQ-36). The attempt is recorded and no result is stored. The backend never maps a non-finite value to a number, to a qualifier, or to a pass/fail.
  - **Arithmetic.** The backend evaluates every gate quantity with Python `decimal`, using a context of precision 50 and rounding `ROUND_HALF_EVEN`. Division, `log10`, and `sqrt` use that context. Within a formula, products are formed first and a single division is done last. Recovery is (spiked − unspiked) × 100 ÷ nominal spike. A limit is calibrator × DF ÷ mg/mL. So a quotient that is exact in decimal is exact here.
  - **Bounds are inclusive** in every `limit_compare`: at most, at least, and within. A value equal to the bound passes. The bounds are values bound in the configuration, not hardcoded in code (CALC-REQ-23).

  - Example (not a requirement, not a default): an LAL configuration binds |r| at least 0.980, %CV at most 25%, spike recovery within 50–200%, dilution at most its dilution bound, and the sample result at most its result limit. The framework must treat each of those comparisons as inclusive. Those numbers are not the rule.

  - Constants that would hold those bounds are parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). This supersedes the earlier stance that this acceptance criterion waits on [#257](https://github.com/Marc02130/nimblelims/issues/257) (closed, absorbed into [#258](https://github.com/Marc02130/nimblelims/issues/258)).
  - **Display.** Rounding is for display only. The stored calculated value is the unrounded decimal. The number of decimals displayed is the significant figures on the analyte or on the analysis/analyte (CALC-REQ-28). No gate reads the displayed value. This Spec does not pick a second global number of display decimal places, and it does not add a stored precision column.
  - AC: rounding a value to fewer decimal places before a compare is a failure of this rule. Recovery computed from decimal strings is exact in decimal. A value equal to a bound passes. A hardcoded bound in code fails this rule. Constants that would hold a bound are parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). This supersedes the earlier stance that this acceptance criterion waits on [#257](https://github.com/Marc02130/nimblelims/issues/257) (closed, absorbed into [#258](https://github.com/Marc02130/nimblelims/issues/258)) (Marc, 2026-11-10). A stored gate result that followed a binary value where the decimal is the exact result fails this rule. Gate inputs in request and response bodies are JSON strings, not JSON numbers; a JSON number in a gate input is refused. A fit output from R arrives as its shortest round-trip string and is stored as that decimal. A dilution equal to its bound is allowed. An absolute correlation just below its bound fails, and rounding it onto the bound before the compare fails.

  - Example (not a requirement, not a default): the strings `0.026`, `0.001`, and `0.05` give recovery 50, and `0.171`, `0.071`, and `0.05` give 200; a dilution of 5000 against a bound of 5000 is allowed; |r| = 0.97995 fails a bound of 0.980, and rounding it to 0.980 first fails; the string `-0.98` passes an inclusive bound of 0.980. The framework must do that decimal compare. Those numbers are not the rule.

  - The contract test stubs the R client to return the shortest round-trip strings for the value and bound under test, and the backend parses them without turning them back into binary. The serialiser that produces such strings is the unit test in CALC-REQ-5. An R output of NaN or Inf stops the stage with `r_non_finite` and stores no result. The R service has no route that computes a replicate mean, %CV, recovery, the dilution step, a unit conversion, a limit comparison, or a subtraction. The stored row has the unrounded value, the decimals displayed are the significant figures on the analyte or the analysis/analyte, and the displayed rounding is not what the gate compared. A stored display-precision column on the result row fails this rule. `analysis_analytes.significant_figures` is the shipped display field and is not that column.

## 5. Out of scope

Stated explicitly, and not built by this Spec:

- A **required validation gate** before activation or use. Validation state and the activation review are recorded only (CALC-REQ-35, CALC-REQ-45).
- **Electronic signatures.**
- **21 CFR Part 11** compliance.
- Any new required reason other than the unpublish reason (CALC-REQ-36, CALC-REQ-56). This Spec does not name that reason's allowed values or its format (OQ-CALC-43).
- IC50 as the stress-case reference. The stress-case reference is the STE-1.2 LAL assay, and it is a test fixture only (CALC-REQ-43, OQ-CALC-24).
- Instrument-data parsers. The configuring agent builds them. This Spec does not specify them (CALC-REQ-47, OQ-CALC-20).
- qPCR as a product assay.

- Example (not a requirement, not a default): per-value knockout and an agreement window.

- The agreement-window value a calculation uses is a configurable value embedded in the calculation (CALC-REQ-54). Constants that would hold it are parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). [#258](https://github.com/Marc02130/nimblelims/issues/258) lists eleven identifiers, including `min_in_range` and `max_remaining_span`, and does not use the words agreement window. This Spec does not equate those names. The first slice stays the ELISA and LAL fixtures (OQ-CALC-24).
- Experiments writing official `results`. Experiment calculation. Single-test reset is parked (OQ-CALC-37).
- A parser-mapping correction. That path is open (OQ-CALC-29). A wrong upload is re-upload.
- Statuses in general, including what cancel does to Tests and what requeue does ([#254](https://github.com/Marc02130/nimblelims/issues/254), OQ-CALC-30). This Spec does not design the lifecycle. Shipped create-as-draft-then-start collides with create-equals-start (CALC-REQ-56).
- The analysis/analyte versioning copy-and-edit UI ([#255](https://github.com/Marc02130/nimblelims/issues/255), OQ-CALC-31).
- Selecting or importing values on experiment init, LIMS run init, or entry init ([#256](https://github.com/Marc02130/nimblelims/issues/256), OQ-CALC-32). The fact that imported values populate experiment data and experiment sample data is in CALC-REQ-50. The UI and the triggers are not designed here.
- A constants table holding constants usable within a calculation, incorporated into the calculation configuration ([#258](https://github.com/Marc02130/nimblelims/issues/258), CALC-REQ-41, OQ-CALC-33). Not implemented in this build. Parked toward [#258](https://github.com/Marc02130/nimblelims/issues/258). [#258](https://github.com/Marc02130/nimblelims/issues/258) lists eleven constant identifiers and says Spec values go in that table. The identifiers are the example under Calculation constant. Not an acceptance range for a result. Not collapsed into analysis/analyte valid ranges.
- A structure holding acceptance ranges for QC type, keyed on QC type and `analysis_analyte` ([#259](https://github.com/Marc02130/nimblelims/issues/259), OQ-CALC-47). Not part of the calculation in this build. Parked toward [#259](https://github.com/Marc02130/nimblelims/issues/259). [#259](https://github.com/Marc02130/nimblelims/issues/259) describes that structure, a table keyed on QC type and analysis analyte; it is not yet designed.
- The table name `lims_run_workspace_results`, and the columns `official_set_id`, `superseded_at`, and `superseded_by_set_id`.
- Any change to other features' behavior or docs. Implementation of this Spec.
